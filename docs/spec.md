## Ethos — CORE (settled 17 Oct)

Every later decision is checked against this. It is also part of the pitch.

**No data collection. No location requests. Nothing leaves the user's own server and devices.**

Hard rules (no exceptions):

- No telemetry, analytics or usage stats — not even opt-in. No crash reporting services (no Sentry etc.); logs stay local.
- No location access, ever. The app never asks for the device's location. Country/units default from the browser/OS language setting or the user's choice — never geolocation.
- No phoning home: no licence checks, no "news" feed. **No automatic update checks unless the admin switches them on; never sends anything about the install** (rule changed by cabledrawer 17 Oct — see section 7, Updates). Users can also learn of updates via GitHub releases / their own tools (Diun, Renovate).
- No third-party assets at runtime: all fonts, icons, scripts bundled in the image — no CDNs, no Google Fonts.
- **Licence notices (cabledrawer 12 Nov):** "Other open-source parts" stays out of Settings → About for 0.9.0 as long as the image carries the other libraries' licence notices. It does: the Python libraries keep theirs in the image's virtual environment (each package's dist-info), and the web build writes `third-party-licences.txt` (every production library and the bundled fonts with their licence texts), served at `/third-party-licences.txt`. A licences screen in About is a 0.9.5 follow-up.
- Recipe images are downloaded at import and stored locally, never hotlinked (hotlinking would ping the source site every time a recipe is viewed).
- Companion apps, if any: no analytics or ad SDKs; app store privacy label "Data not collected".
- No account with the developer — nothing to sign up for.

**Outbound connection rule (settled 17 Oct):** outbound connections happen only when the user triggers or configures them. Each one is clearly labelled and switched off until the user sets it up. The README gets a "Privacy" section listing every possible outbound connection. Settings → Privacy shows the same list, each with its own switch, under "Nothing leaves this server unless you switch it on, or press Check now in About." (proposed, for cabledrawer, 12 Nov: Check now connects when pressed) Known cases:

- Recipe URL import: the server fetches the page the user asked for (that site sees the server's IP). User-triggered.
- Update check (cabledrawer 17 Oct): "Check now" (admin click) or an optional daily check, off by default (the switch controls only the daily check; Check now always works, cabledrawer 12 Nov). One plain request to GitHub's public release list; GitHub sees the server's IP, nothing else is sent.
- Notifications (not built before 1.0, cabledrawer 18 Oct): go only to the services the user configures (their own ntfy/Gotify/email, or a public one they choose). Nothing configured = nothing sent.
- Single sign-on: talks only to the user's own identity provider.
- Barcode lookups (Open Food Facts; not in 1.0): opt-in, or use a downloaded offline copy of the OFF database (several GB).
- Phone push (not in 1.0): pushes carry no content ("You have an update"), or users route them through their own ntfy (UnifiedPush) instead.

## UX — CORE (in progress 17 Oct)

**Why:** cabledrawer "absolutely hates" Mealie's and Tandoor's UIs — in his words: clutter, too many clicks, utterly unintuitive, and they look bad. Specific failure: in the meal planner you can't simply drag a recipe to copy it, or turn it into leftovers. For an app competing with them, the UI is the product. Looks matter as much as flow — visual quality is a requirement, not polish.

**Visual references (cabledrawer 17 Oct):** Monzo (calm, white space, rounded cards, one main action per screen, big friendly numbers, plain warm language, small satisfying feedback) and the Notes app on iPad (content first, almost no chrome, sidebar + content split, quiet paper-like reading). Translation: Today/Plan/Shopping feel Monzo-like; recipe pages feel Notes-like; desktop/iPad use a sidebar, phones use bottom tabs.

**Platform emphasis (settled 17 Oct, cabledrawer's words: "Desktop and phone = but preference to phone - desktop isn't disadvantaged"):** desktop and phone are both full first-class targets for the v1 web app. Where a trade-off has to be made, phone wins — but never at the cost of a worse desktop experience. Desktop gets its own layouts (sidebar, wide week grid, three-pane recipes), not a stretched phone UI.

### Principles

1. **Phone and desktop both first-class; phone breaks ties.** Big tap targets everywhere; bottom tabs on phone; sidebar on desktop; each layout designed for its device.
2. **Today first.** Home answers: what are we eating, which tubs are left, what needs using up, what do we need to buy — not a recipe grid.
3. **Few taps for common actions.** Tick an item = 1 tap; add to list = 2 taps; log a batch cook in under a minute.
4. **Nothing to set up before it's useful.** Sensible defaults for units, shops, locations; setup optional, never a wall.
5. **Hide the advanced stuff.** Density, conversions, aisle order behind "more", only when needed.
6. **Undo, not "Are you sure?"** Actions happen instantly with an undo toast (Ctrl+Z on desktop). There are three justified exceptions, where asking first is kinder than Undo: signing out with changes that were never sent (they can't be undone), removing a line from the shopping list with its amount box's Remove (cabledrawer 20 Oct, hand test; the swipe's Remove goes at once with Undo, F77, cabledrawer 28 Oct), and Drafts' "Save your changes?", which protects unsaved work (cabledrawer 28 Oct, review of v0.6.0).
7. **Plain words.** "Cupboard", "use soon", "tubs left" — never database words like "food items", "units", "labels", "groups".
8. **Fast and calm.** Instant (optimistic) updates; restrained visual style; one consistent component set / design system.
9. **Accessible.** WCAG AA, large text support, real dark mode.
10. **Tested on real people.** A non-technical person tries it doing real tasks, at 0.9 with the private trial (cabledrawer 19 Oct).
11. **Direct manipulation** (from cabledrawer's planner complaint). Things on screen can be picked up and moved: drag to move, drag to copy, drag to spread as leftovers — with tap-based equivalents on phones where dragging is awkward. Every drag has undo.
12. **Use the screen** (cabledrawer 17 Oct). Dense-but-calm layouts on desktop: no wasted space, especially on the Plan screen.
13. **Dark mode toggle in plain sight** (cabledrawer 17 Oct — "pet peeve"). Three-way Auto · Light · Dark switch visible in the sidebar (single cycling button when collapsed; on phone, in the household/settings sheet) — never buried in settings. Choice saved per user. Dark mode is a properly designed theme, not inverted colours.
14. **One scroll direction, no chunky scrollbars** (cabledrawer 17 Oct). Every screen scrolls vertically only — never sideways at page level. On phones the header, bottom tabs and bottom action bar stay fixed and only the content between them scrolls (long recipes, lists); scrollbars are hidden/overlay like native apps. Desktop pages scroll vertically with thin scrollbars.
15. **Toggles are click-to-switch** (cabledrawer 17 Oct, from canvas comments). Anything that can be on/off (an ingredient in the "Cooked it" review, "remember for next time", meal slots, outside connections) is a real switch you click or tap, the same on phone and desktop — not a checkbox in one place and a button in another.
16. **Always show whether you're connected** (cabledrawer 17 Oct). The app shows plainly when it can't reach the server and when it's back, so nobody wonders whether their ticks were saved. Calm, not alarming: nothing extra while all is well; an "Offline — 3 changes waiting" bar when disconnected (above the bottom tabs on phone, at the foot of the sidebar on desktop, with a small dot when collapsed); a short "Back online — all saved" toast on reconnect. Offline changes still happen instantly (principle 8).

### Meal planner interactions

- Drag a recipe from the recipe tray onto a day/meal slot → planned (or added to a meal that already has food).
- Drag a planned meal to another slot → on drop: Move (Enter) · Copy (Alt) · Leftovers here.
- "Cook once, eat for…" on any planned meal → pick portions (and people) → following slots fill as linked leftover tubs ("tub 2 of 4", same colour as the cook day), or the user picks the slots themselves. Drag a tub to rearrange; remove one → back to "tubs left" (or freezer).
- Phone: long-press a meal → Move to… · Copy to… · Leftovers on… with a day picker.
- Undo for every planner action.

**Decided for the 0.6 Week and Month screens (cabledrawer 26 Oct):** cabledrawer accepted every choice in PR 3 ("20 items per meal, 12 slots, plan changes online only, cooked/not-cooked/moved meals locked, Leftovers copies until PR 4, slot settings later"). In plain words:

- **Caps:** at most 20 things in a meal and 12 meal slots in a household.
- **Plan changes need the server,** like the Pantry: there's no offline queue for the plan, and offline the plan's buttons are greyed out with the usual wording.
- **A meal that was cooked, not cooked or moved is locked:** it can't be changed from the plan, and Undo leaves it alone.
- **"Leftovers" copies the meal** until Cook once makes real tubs (0.6, step 4). A tub is never copied.
- **Slot settings come later,** with the Settings screen for the plan: renaming and reordering slots, the first day of the week, and how far ahead the shopping list looks.
- **Days:** a day more than 1 year back or 2 years ahead can't be planned, counted from the household's own today.
- **A meal's kcal** is one serving of each recipe in it.
- **Dropping a recipe on a Month day** puts it in the last empty meal that's switched on.
- **The plain drop is Move** (Alt copies); Copy and Leftovers have their own drop zones.
- **Tub actions wait for tubs** (0.6, step 4): "Whose tub?", "To freezer" and "Fill from freezer first".
- **The new words** are in `docs/dev/words.md` section 19.

### Visual system used in the mockups (draft, easy to change)

- **Dark:** deep green-black ground, slightly lighter cards for layering, soft off-white text (not pure white); batch colours stay solid on cook days, tubs become dark tints with light text; accent green and "use soon" orange brightened for contrast; recipe reading pane a shade darker with slightly dimmed serif text.

### Keeping the UI good (cabledrawer 18 Oct, from 0.4)

Seven habits taken from apps known for good front ends (GOV.UK, Monzo, Linear, Apple). All start in 0.4. 0.4's first pull request sets up the tools (word list, gallery page, stress screenshots, size limit, saved screenshots) before any recipe screen is built.

1. **One word list.** `docs/dev/words.md` holds every on-screen term and wording rule in one place: the words we use and the ones we never use (for example "ingredient", never "food"; "tubs left"; "use soon"), how buttons are worded, how toasts and Undo read, and how error messages are built (what happened, then what to do). It starts from the wording already decided in this spec and the built screens. cabledrawer approves the first version and any change to it. The checker checks every pull request's on-screen text against it.
2. **Every state, not just every screen.** Each screen is built and checked when it is empty, loading, failed, offline, with one item, with many items (200+), with very long names (for example long Tamil other names), and with text at 200% size. The review screenshot script takes one extra "stress" shot per screen (many items, long names, large text).
3. **A component gallery.** A page at `/dev/gallery` shows every shared component (buttons, switches, sheets, toasts, fields, chips, empty states) in all its states, in light and dark. It exists only in development builds and is never shipped in the image. New screens use components from the gallery; a new component, or a new kind of an existing one, is added to the gallery in the same pull request. The checker screenshots it. No Storybook or similar tool (they add many dependencies and some collect usage data); it is an ordinary page in the app.
4. **Bugs and paper cuts first.** At the start of each milestone the friction log is sorted into three piles: fix now, later (with a milestone), or "Not planned". Nothing sits unsorted. Known bugs are fixed before new features. Each milestone ends with a small "paper cuts" pull request for the fix-now pile, before the release pull request.
5. **Speed is checked, not assumed.** `./check` fails if the largest single page grows past a size limit. A page's size is everything a browser fetches to open it, its JavaScript and CSS with the code it shares with other pages, compressed the way it's sent. The total of the whole app is printed for information but not checked (cabledrawer 21 Oct: "change it to measure the largest single page instead of the total … Keep the total shown in the check's output for information, not as a pass/fail."). The limit is 144 KiB, 25% above the largest page in 0.4, the recipe editor at 114.8 KiB (cabledrawer 21 Oct: "Yes: the size limit is 144 KiB, measuring the largest page including the shared code and the styles (25% above today's 114.8 KiB, my 25% rule)."); raising it needs cabledrawer's OK. A browser test on a simulated slow phone checks that the common actions (tick, add, open a screen) show their result straight away.
6. **Saved screenshots.** A few key screens (Today when built, Pantry, Shopping, Recipes, the gallery), phone-light and desktop-dark, have approved screenshots saved in the repo. `./check` fails if they change. When a change is intended, the pull request updates them and says so, and the checker looks at the before and after.
7. **Calm motion and keyboard use.** Animations are small and turn off when the device asks for reduced motion. Every desktop screen can be used with the keyboard alone, with a visible focus ring; a browser test tabs through each one.

## 1. Vision and audience (settled)

**One-liner:** A self-hosted kitchen app that knows what's in your cupboards. You plan meals and batch cooks, it builds your shopping list from what's actually missing, keeps the pantry up to date as you shop and cook, and shows nutrition per serving where the recipe provides it.

**Audience:** broad, not just cabledrawer's household.

- **Meal prepper:** cooks in bulk once or twice a week, portions it out over several days. Needs batch planning (cook day → portions → days covered), scaling, leftover-portion tracking, nutrition per portion.
- **Pantry family:** 2–5 people, one or two plan, everyone adds to the list and shops. Needs accurate stock, a shared live shopping list, use-before-expiry, a simple UI.
- **Shared need:** import recipes from the web; a shopping list that's right, not padded with things already in stock.

**Positioning:** Mealie/Tandoor have good recipes but shallow inventory and cluttered, unintuitive UIs; Grocy has real stock but a warehouse-style UI and clunky recipes/planning. Mealwright puts pantry + meal prep at the centre, recipes in support, with a clean UI — and a strict privacy ethos.

**Nutrition (decided 17 Oct):** per serving: calories, protein, carbs, fat and fibre — only where the recipe supports it, i.e. taken from the recipe's own nutrition data (schema.org NutritionInformation on import, or the user typing it in). The app does not calculate nutrition from ingredients in v1, so no food nutrition database is needed. Batch portions re-divide the recipe total when portion count differs from the recipe's servings. Missing fields shown as unknown, not zero. Flag nutrition as possibly out of date if the ingredients are edited after import. No daily intake log or per-person targets.

- Open question: calculate from ingredients as a fallback later (post-v1)?

**Non-goals:**

- Not a hosted/SaaS service; self-hosted only
- Not a social/recipe-sharing site
- No grocery store or delivery integrations
- Not a diet/intake tracker or medical/clinical tool; numbers only, no guidance

**Foods and units (cabledrawer 17 Oct)**

**Pantry (cabledrawer 17 Oct)**

- Stock with quantity, unit, location (fridge/freezer/cupboard; renameable, can add more e.g. spice rack)

- Count foods (cabledrawer 17 Oct): things like onions, eggs, lemons are tracked by number in the pantry ("5 onions"), not converted to grams. A recipe that says "2 onions" takes 2; a recipe that gives grams for a count food is converted using the per-item weight and shown/rounded as a count (to the nearest half).
- "How much did you use / how much is left?" (cabledrawer 17 Oct): the user can always override the calculation — enter what they used ("used 1½ onions") or what's left ("3 left") — both in the "Cooked it" review and directly on any pantry item.
- **Amounts on screen are rounded (F132, cabledrawer 3 Nov):** in Cook mode's Cooked review, g and ml under 10 show to one place, 10 and over whole; an amount above 0 never shows as 0 (it shows as 0.1), and 0 stays 0. Counts are unchanged (¼ ½ ¾, else two places). Only the screen changes; the stored numbers don't.

**Cooking — how deduction works (agreed 17 Oct)**

1. Recipe ingredients and pantry stock are linked by food and stored in a common unit (g / ml / count).
2. Scale to what was cooked: needed = recipe amount × portions cooked ÷ recipe servings.
3. Convert only when units differ: weight↔weight direct; volume↔volume fixed maths (1 tbsp = 15 ml); volume↔weight via a per-food grams-per-cup value; count↔weight via per-item weight. Conversion values from a bundled offline table of common foods (candidate source: public-domain USDA food weights — verify licence in the release step). Unknown conversion → ask once, remember for the household (cabledrawer decided 17 Oct; e.g. "About how much does 1 cup of toor dal weigh? Suggested: 200 g"). The question carries a "Remember for next time" switch (on by default); remembered sizes can be reviewed in Settings → Amounts.
4. Take from the pack that expires first; fridge/cupboard before freezer (freezer only if the user says).
5. "Cooked it" review shows every proposed deduction (e.g. "−200 g toor dal, 800 → 600 g"; "−2 onions, 5 → 3"), each adjustable as used-or-left and each with an on/off switch to leave it out, then one-tap confirm; Undo afterwards.
6. Staples never deducted. Stock never below zero → offer "add to list"; optional per-food "running low" level → same offer. Pack sizes supported ("1 packet = 500 g", part-used shows what's left).
7. Batch cooks deduct ingredients once on the cook day and create the tubs; eating a tub uses the tub, not the ingredients again.
8. Aim: "roughly right, easy to fix" — quick corrections in the pantry and Undo in Recent changes.

- Week view and month view
- Meal slots: default Breakfast, Lunch, Snack, Dinner — all optional; households can rename them to anything and add their own
- A meal can hold several recipes/items (recipes, tubs, plain foods)

**Users:** several users per household, Admin/Member roles, API tokens, single sign-on (OIDC) from v1.0 (cabledrawer 17 Oct) alongside local logins

## 6. Data model (main decisions settled 17 Oct)

### Offline shopping-list sync (decided 17 Oct)

**Why it is the risk:** ticking an item also adds it to the pantry, so two people shopping offline could double the stock. The list itself is easy; the pantry side effect is the hard part.

**How it works:** the phone keeps a queue of actions (tick, untick, add, change amount, delete, put away). Each action gets its own ID made on the phone. On reconnect the phone sends the queue and the server works through it in the order it receives it (a server counter, not device clocks). An action sent twice (same ID) is ignored. Only the server changes pantry stock. The protocol is part of the public `/api/v1`, so future phone apps use it too. Chosen over sending and replacing the whole list (loses the other person's edits) and over shared-editing libraries / CRDTs (weak Python server support, and the pantry rules still need the server).

**Rules:**

- **A tick sticks.** If anyone ticked an item, it's bought; an untick counts only if it comes after the tick.
- **Both ticked the same item offline (cabledrawer 17 Oct):** counts as two purchases — both go into the pantry — and once the phones reconnect the app asks plainly: "You and Wren both ticked toor dal. Did you buy 2?" → Yes, 2 · Just 1. Shown as a card on Shopping (and Today), not a blocking pop-up; "Just 1" removes the extra, with Undo.
- **A hand edit beats the app's own sums.** When the plan changes, the list updates amounts it worked out itself, never one a person typed. Plan-made items are keyed by food + shop so regenerating updates them instead of duplicating.
- **The saved list first, then the plan (cabledrawer 27 Oct):** Shopping shows the saved list at once, online, slow or offline, as it has since 0.3. The update from the plan runs afterwards, in the background, and never makes the list wait; if it changes anything, the list is read again.
- **Deleted stays deleted.** Deletes leave a hidden marker (tombstone) so an old offline phone can't bring an item back.
- **Put away offline (cabledrawer 17 Oct):** choosing Fridge/Freezer/Cupboard while offline is queued with the tick.
- **When an offline tick happened (cabledrawer 2 Nov):** "an offline Shopping tick uses the phone's time, unless that time is in the future or clearly wrong, in which case it uses the server's time." The phone's time is corrected for a phone clock that runs fast or slow, as for Undo (section 9). **Clearly wrong** (cabledrawer 2 Nov: "7 days OK"): missing, impossible, or more than 7 days before the server receives the tick (a weekend away is about 3 days). This replaces the 21 Oct catch "an offline tick is dated when the phone sends it". It dates the tick, so a staple's restock date (K5) and the purchase it puts in the pantry follow when it was really bought.
- **No conflict pop-ups.** Other clashes show as a quiet note ("Wren ticked this too") with Undo.
- **How long offline (cabledrawer 17 Oct):** plan for a weekend away (about 3 days). The phone keeps the shopping list, recently viewed recipes and the queue for that long; older queues are still applied, never thrown away. (The Recipes, Ingredients and Pantry lists are no longer promised offline: changed by cabledrawer 31 Oct, see "What works with the server down".)
- **Connection status:** see UX principle 16.
- **Offline wording grows with PR 6 (cabledrawer 18 Oct):** until the offline queue arrives (0.3 PR 6), changes made offline aren't kept on the phone, so the wording says only what is true. Shopping's subtitle while offline says "12 to buy · offline", and the toast on reconnecting says "Back online". PR 6 adds ", saving on this phone" ("… on this computer" on desktop) and "— all saved" once they are true. Extra lists say just "Extra list · 5 · offline" while offline, in PR 5 and after PR 6 alike: only the main list's subtitle grows (cabledrawer 18 Oct).
- **Opening the app offline (cabledrawer 18 Oct, PR 6):** the app opens as the person last signed in on that phone, and Shopping works from the phone's copy. Pantry, Ingredients and Settings stay online-only in 0.3; offline they show a short note, "You’re offline." and "Pantry needs your Mealwright server. Your shopping list works offline." (two sentences with no dash since 0.4, by ruling 4 of the word list, cabledrawer 19 Oct; naming the screen: Ingredients, Settings), with a Shopping button. The bar still shows Offline. Settings keeps two parts offline under that note: Sign out, and the theme switch, which is saved on the device so it works without the server (cabledrawer 18 Oct: "Keep it visible"). The "+ Add to pantry" button also stays visible offline, as a normal button: tapping it doesn't open the sheet, it shows "Adding to the pantry needs your Mealwright server. Try again when you're back online." (cabledrawer 18 Oct).
- **A phone that has never loaded the list, opened offline (cabledrawer 18 Oct, PR 6):** Shopping says "Your shopping list isn't on this phone yet. It'll be here after you've opened it once while connected."
- **Opening offline or on a weak signal shows the saved copy at once (cabledrawer 20 Oct, hand test):** Today and the saved shopping list show at once, and the network is tried in the background; when it answers, the list updates in place, as with live updates. In 0.3.0 a weak signal held a blank screen for 30–40 seconds and then "Loading…" for over 40 seconds. How it's done was proposed by the builder and agreed by cabledrawer (21 Oct: "the proposed numbers are OK: wait at most half a second for the server at start; the tests allow 1.5 s for “about a second”; changes due at about the same moment go together in one send." and "keep the sign-in page (as built). No self-restart: the spec rule that the app never reloads itself stays. The extra password entry in this rare case is fine."): the start waits at most half a second for the server before opening as the person last signed in on that phone; waiting changes start sending at the same time as the list shows; and if the server then names another login, that login goes to the sign-in page (nothing is wiped while the screen is up, and the app doesn't reload itself). Details in the sync protocol, 11.4 and 11.6. Coming in the 0.4 paper-cuts PR (cabledrawer 21 Oct: "(a) after a slow start, ask the server again who is signed in; (b) signing out clears the household's shops and places held in memory, so nothing carries over to the next person.").
- **"This phone" or "this computer" (cabledrawer 18 Oct, PR 6):** chosen by layout. With the bottom tabs the app says "this phone"; with the sidebar it says "this computer", so a tablet held wide says "computer".

**What this adds to the data model:** list items with phone-made IDs, source (from plan / typed by hand), "hand-edited" flag, ticked by / when, put-away location, deleted marker, version number; a sync log of applied actions (action ID, user, device, type, server order, applied time) for repeat-detection and Undo; a "both ticked" question record until answered.

**Decided for 0.3 (cabledrawer 17 Oct):**

- **Same login on two phones:** if one login ticks the same item on two phones while offline, the app still asks "Did you buy 2?", worded "This was ticked on two phones".
- **Sign-in runs out while offline** (not a sign-out): the waiting changes stay on the phone and are sent once the same login signs back in. If a different login signs in, the sign-out warning comes first.
- **Ticking into the pantry:** the item goes to the food's usual place, or Cupboard if it has none, with no use-by unless one is chosen.
- **Items that aren't food** (kitchen roll, soap): every list item is still a food. A non-food item becomes a food with the Staple switch on, so ticking it never adds pantry stock.
- **Aisles:** each food has an optional Aisle (under "more" in the editor). Default aisles: Veg & fruit · Meat & fish · Dairy · Bakery · Dry goods · Tins & jars · Spices · Frozen · Drinks · Household · Other (cabledrawer added Meat & fish, Tins & jars and Drinks: Mealwright is for the public). Each shop orders the aisles by dragging (Shops & places, 0.8); until then shops use the default order. Aisle headings on Shopping use these names, not the older ones in the mockups ("Fruit & veg", "Rice & grains"), and the Aisle field arrives in 0.3.
- **What the phone keeps offline:** in 0.3 the app itself and the shopping lists; recently viewed recipes from 0.4. (Changed by cabledrawer 31 Oct: the Recipes list is no longer kept for offline; see "What works with the server down".)
- **App updates:** a new version installs quietly the next time the app is opened, never mid-shop, and waiting changes are always sent first. The very first version on a device takes the page that installed it once its files are saved, so that first page also works with no connection; an update never does (proposed, for cabledrawer, 15 Nov). Docs note that offline needs HTTPS, and that iPhone Safari can clear a web page's offline data after 7 days without use (adding it to the Home Screen helps).
- **No new libraries needed:** Server-Sent Events are built into FastAPI; SvelteKit's own service worker support is used. `idb` (ISC, very small) is approved for the IndexedDB queue (cabledrawer 17 Oct); the pull request that builds the queue pins an exact version released at least two weeks earlier. Well-tested code matters more than one package fewer.
- **A tick against a delete** (both offline): the tick still counts as bought, so the pantry gets the stock, and the item stays off the list. The person who ticked sees a quiet note, "Wren had removed this. Your tick still went into the pantry", with Undo.
- **Unticking after a tick** takes the stock back out the way Undo does: if some has been used since, only what's left comes out, never below zero.
- **Both add the same ingredient** offline (same list, same shop, neither ticked): it stays one line, keeping the bigger amount, with a quiet note ("Wren added milk too") and Undo. The "same list, same shop, neither ticked" wording is confirmed (cabledrawer 18 Oct).
- **Both change the same item's amount** offline: the change the server receives last wins, with a quiet note.
- **"Did you buy 2?"** shows to both people who ticked. The first answer settles it and the card disappears for the other person. Until 0.6 the card shows on Shopping only; Today gets it with 0.6.
- **Ticked items** fold into an "In the trolley · N" row at the end of each shop. "Clear ticked" removes them, with Undo.
- **Ingredients with no usual shop** go in an "Any shop" section, shown last.
- **Typing something that isn't an ingredient yet** makes it a new ingredient, asking "How do you count it?". A blank amount means one of its usual size, or 1 if it's counted in items.
- **Extra lists** can be renamed and removed, with Undo. The main list can be renamed but never removed.
- **Main list subtitle:** "12 to buy · synced with Wren", or "12 to buy · saved" in a one-person household.
- **Signing out with unsent changes:** "3 changes haven't been sent yet. If you sign out now, they're lost." Buttons: Try sending now · Stay signed in · Sign out and lose them. This is one of the three justified exceptions to "Undo, not Are you sure?" (UX principle 6): changes that were never sent can't be undone. The others are removing a line from the shopping list with its amount box's Remove (cabledrawer 20 Oct; see "Shopping rows" below) and Drafts' "Save your changes?" (cabledrawer 28 Oct, review of v0.6.0). If the phone can't check what's waiting (its offline store can't be read): "This phone couldn't check for changes waiting to be sent. Nothing has been deleted." Buttons: Try again · Stay signed in · Sign out anyway — anything waiting on this phone may be lost (cabledrawer 18 Oct).
- **An item with no amount** (weighed or measured, with no usual size): ticking it puts nothing into the pantry, and the ticked row offers "How much?" for one more tap if you want it counted. No prompt (cabledrawer 18 Oct).
- **"How do you count it?"** is asked once, when a typed name is a brand-new ingredient: By weight · By volume · One by one · Don't count it (a staple, for kitchen roll and soap). When connected to your Mealwright server, the bundled table's guess is picked first (the table is on the server; nothing is looked up on the internet) (cabledrawer 18 Oct).
- **Put away on two phones** with different places: the one the server receives last wins, with a quiet note ("Wren put coriander in the Freezer") and Undo (cabledrawer 18 Oct).
- **A different login on a phone holding someone's unsent changes:** the sign-in page says "Wren's 3 changes are waiting on this phone. Sign in as Wren to send them." If someone else signs in anyway: "Wren's 3 changes haven't been sent yet. If you carry on, they're lost." Buttons: Sign in as Wren instead · Carry on and lose them. Carrying on wipes the phone's offline copy, as signing out does (cabledrawer 18 Oct). Right after the app has signed someone out for this reason, the sign-in page says why, in place of the first line: "You were signed out because Wren's 3 changes are waiting on this phone. Sign in as Wren to send them." With one change: "You were signed out because Wren's change is waiting on this phone. Sign in as Wren to send it." On a computer it says "this computer" (cabledrawer 18 Oct). If the phone can't check what's waiting, the same login carries on (it never wipes anything); anyone else gets "This phone couldn't check for changes waiting to be sent. Nothing has been deleted." with Try again · Carry on anyway — anything waiting on this phone may be lost (cabledrawer 18 Oct).

The sign-in page says "This phone couldn't delete its offline copy of the household. Nobody can sign in on it until that's done. Close other Mealwright tabs or restart the browser, then Try again." with a Try again button; "this computer" on a computer (cabledrawer 18 Oct). Under that message, one small line: "Still stuck? Clear this site's data in your browser's settings." (cabledrawer 18 Oct).

- **Changing an ingredient's usual shop** moves its unticked items from the old usual shop (or Any shop) to the new one; items someone put under a particular shop on purpose stay (cabledrawer 18 Oct).

"Keep the bigger amount" is only for two people adding the same thing without seeing each other's line (cabledrawer 18 Oct).

### Foods and units (decided 17 Oct)

**Shape:**

- **One food = one thing you buy and cook with** (toor dal, onions, milk). Each food has: name, other names, how the pantry counts it (weight / volume / count / staple), usual place at home, preferred shop, and optional extras (pack size, weight of one item, weight of a cup, running-low level).
- **Stored in grams, millilitres or counts** behind the scenes; the recipe's own wording is always kept.
- **Conversions in two layers:** a built-in table shipped with the app, with the household's own answers on top. Household answers always win; app updates never overwrite them.
- **Every recipe ingredient points to a food;** anything the app can't match goes to the Import review screen.

**Close cousins (cabledrawer 17 Oct):** the user decides whether two things are one food or two (e.g. "onion" and "red onion"), using the existing "Same as <food>" / "New food" choice, and can merge or split foods later. v1.0 also has an optional **"Can use instead"** link between foods (red onion can stand in for onion). With a link set:

- The shopping list counts stock of the stand-in. It doesn't add onions while you have red onions, and shows a quiet note: "Using red onions you have".
- The "Cooked it" review takes from the stand-in and shows it on that row, with its Use switch as usual.
- The link goes one way unless the user sets it both ways.

**Brands (cabledrawer 17 Oct):** no brand tracking. A brand only appears if the user types it as part of a food's name (e.g. "MDH sambar masala"), and then it is simply its own food. There is no separate brand field. Pack size stays.

**Other names (cabledrawer 17 Oct):** in v1 households add their own other names for a food (e.g. thuvaram paruppu, arhar dal → toor dal). Import matching uses them. Built-in name profiles for ingredients (e.g. Tamil / Hindi name sets) are not in 1.0.

**Ingredients screen (cabledrawer 17 Oct):** not its own top-level section. It sits under Recipes — the sidebar shows a tree: Recipes → All recipes · Drafts · Ingredients; on phone the All recipes screen has Drafts and Ingredients buttons at the top. **Removing an ingredient (cabledrawer 17 Oct):** the Ingredients editor has a **"Remove from Ingredients"** button, which deletes that food's record entirely. It appears only when nothing depends on the food: none in the pantry and not on any shopping list. Recipes do not block it (cabledrawer 19 Oct, 0.4): each recipe line that used it keeps its words and shows "not linked", and Undo links it again. The made-ahead ingredient of a recipe can't be removed while Made ahead is on (cabledrawer 19 Oct, 0.4); see "Made ahead" under the 0.4 decisions. Like every change it can be undone for 7 days. **Words (cabledrawer 17 Oct):** on screen it's always "ingredient", because the screen is called Ingredients; "food" is the internal word in the data model and code and is never shown. Inside a recipe (0.4) the action is "Take out of this recipe", never "Remove", so the two can't be confused. **After the 7 days (cabledrawer 17 Oct):** a removed ingredient is then deleted for good, with its other names, sizes, links, remembered answers and its monthly history totals. Only the newest removal line for an ingredient can have Undo, and only while the ingredient is still removed; this is worked out when the list is read, and any other removal line's Undo is refused (cabledrawer 21 Oct: "No Undo on the "is back" line." and "only the newest removal line for that ingredient can have Undo, and only while the ingredient is still removed"). Built in 0.4 PR 7. When the change that brought it back is undone and the ingredient is removed again, the line shows as undone, the same way any other undone line looks (cabledrawer 21 Oct: "after the add that brought Lemon back is undone, mark "Lemon is back in Ingredients" as undone, the same way any other undone line looks"): the Undo's "Undid: …" line shows in Ingredients' Recent changes too. **Data model additions:** food "can use instead" links (food → stand-in food, one-way); food merge history (so a merge can be undone and old recipe links still resolve).

### Stock (decided 17 Oct)

**Measure stock the way it's sold (cabledrawer 17 Oct).** Each food has a pantry unit that matches how you buy it, and the app does the maths behind the scenes:

- Toor dal is sold in 500 g packets, so the pantry shows packets ("about 750 g · 1½ packets").
- Bread is counted in slices.
- Eggs are counted one by one. Buying "a dozen" adds 12.
- A food can have more than one way it's sold ("packet = 500 g", "dozen = 12", "loaf = 20 slices"). Each one converts into the food's base amount (grams, millilitres or count).

**Part-used packets (cabledrawer 17 Oct):** after cooking, the app suggests its best estimate of what's left ("about 250 g · ½ packet"). The user can correct it either in grams or as a fraction of the packet. Quick picks are ¼ · ½ · ¾ · full, or you type an amount.

**Marks in the opened pantry row (cabledrawer 18 Oct, from the 0.2.0 hand test):** for a food with a single packet, the ¼ · ½ · ¾ · Full marks show in the opened row, next to the "Used some" box, so they are easy to find. With several packets the row stays as it is, and the marks stay in each packet's menu. Tapping a mark saves at once, with Undo. Under the marks, "About 250 g left · type it instead" opens the packet's "What's left" box; it says "left" so it can't be confused with "Used some" beside it (cabledrawer 18 Oct).

**Tubs (cabledrawer 17 Oct):** counted in quarters. Eating from a tub uses one whole tub by default; a ¼-step stepper lets you say "used ½". Whatever is left stays where it is ("¾ tub") with its batch colour.

**Packets with different use-by dates (cabledrawer 17 Oct):** each packet is kept separately behind the scenes, so the one that goes off first is used first. The pantry shows them together ("1 kg · 2 packets"); tap to see each packet and its date.

**Slices in a loaf (cabledrawer 17 Oct):** the app asks once, the first time bread is bought ("About how many slices? Suggested: 20"), and remembers the answer for the household, using the same "ask once" pattern as cup weights.

**Different pack size on the day (cabledrawer 17 Oct):** when ticking an item off, the user can change the pack size ("1 × 1 kg" instead of 2 × 500 g). No setup is needed, and the new size is added to the food's sale units. **Counted things (cabledrawer 2 Nov):** for a food counted one by one, picking 6 adds 6 to the pantry and makes no new "pack of 6" size.

**Data model:** food sale units (name, amount in base unit — e.g. packet = 500 g, dozen = 12, loaf = 20 slices); stock lots keep the base amount plus the sale unit they were bought in, for display; tub amount stored in quarters (0.25 steps).

### Recipes (decided 17 Oct)

- **Recipes inside recipes, v1.0 (cabledrawer 17 Oct):** a recipe can list another recipe as an ingredient (sambar → homemade sambar powder; dosa → dosa batter). Making the inner recipe puts it into the pantry like any food ("Dosa batter · 1.5 litres · fridge") and the outer recipe takes from it. If there's none, the app offers "Make batter first?". The shopping list works through the inner recipe's ingredients only when there's not enough of it made.
- **Where a recipe came from (cabledrawer 17 Oct):** imported recipes always keep the web address and import date, and show "From: <site>" on the recipe page, crediting the original author. Opening the link is the user's own click in their browser; the server never re-contacts the site. Typed-in recipes have an optional "Source" note ("Tess's", a book title).

**Data model:** recipe ingredient can point to a food or to a recipe; a recipe that can be made ahead links to its own pantry food (homemade); recipe source URL, import date, source note. Guard against loops (a recipe can't contain itself, directly or indirectly).

**Decided for 0.4 (cabledrawer 19 Oct):** cabledrawer accepted all the recommendations in `0.4-questions.md`. In plain words:

- **What a recipe holds.** A name (required, up to 200 characters), an optional one-line description (up to 200 characters; proposed, waiting for cabledrawer), an optional time in whole minutes (up to 14,400; cabledrawer 19 Oct), "Serves" (1 to 99, a new recipe starts at 4, and it can be empty), an optional "Makes" (an amount and a unit, such as 1.5 litres or 12 dosas), tags, nutrition per serving, ingredient lines, method steps, an optional source note (plain text, up to 500 characters; cabledrawer 19 Oct; the server never visits it), and one photo (see Photos below).
- **Photos (cabledrawer 19 Oct).** One photo per recipe, taken from a JPEG, PNG or WebP file of up to 15 MB and 50 megapixels (cabledrawer 20 Oct: recent phones take 48–50 MP photos); what a file is comes from the file itself, not its name. Other files (GIF, SVG, HEIC, damaged files) are refused: "That isn't a photo Mealwright can use. Try a JPEG, PNG or WebP." A bigger file: "That photo is bigger than 15 MB." Too many pixels: "That photo is too big to use (over 50 megapixels). Try a smaller copy." (cabledrawer 20 Oct). The 15 MB is for the photo upload only; everything else the server takes stays at 4 MiB. Every photo is cleaned on our own server: turned the right way up, then rebuilt from the picture alone, so nothing hidden in the file is kept (camera, date, the place it was taken, other notes, thumbnails). Colours are turned into ordinary sRGB, see-through parts become white, and an animated picture keeps its first frame. A JPEG that will be made smaller anyway is opened at a reduced size, so memory stays low (cabledrawer 20 Oct). Two copies are kept, both JPEG: a large one (longest side 1600 px, never made bigger) and a small one for the recipe list (shortest side 156 px, the list's 52 px square at 3×; cabledrawer 20 Oct). The file sent is never kept. The copies are stored in the household's own folder on the data volume, under random names, and only people signed in to that household can see them. Like everything else from the server, photos are sent so the browser keeps no copy of its own (`no-store`; cabledrawer 20 Oct). **Saving (cabledrawer 20 Oct):** "nothing changes until Save" holds for photos too. Picking a photo uploads it straight away and the server answers with its id; the recipe's Save attaches it, replaces the old one or clears it. A replaced or cleared photo is deleted when the recipe is saved, files included. A save that leaves the photo out keeps it; one that says "no photo" removes it; one with a new photo replaces it (cabledrawer 20 Oct). So the editor's "Remove photo" must send "no photo" explicitly (`"photo_id": null`); leaving the photo out never removes it. An upload no recipe has taken within 24 hours is deleted by the server's own hourly clean-up, which never contacts anything outside. A household can have at most 10 uploads waiting to be saved; the 11th is refused with "Too many photos waiting to be saved. Save or cancel a recipe first." Saving one on a recipe, deleting one, or the 24-hour clean-up frees a place. An editor that's cancelled can delete its unsaved upload at once (cabledrawer 20 Oct); a photo already on a recipe is only removed by saving the recipe with "no photo"; trying to delete it on its own is refused with "That photo is on a recipe. Take it off in the recipe, then save." (cabledrawer 20 Oct). Deleting a recipe keeps its photo while Undo is offered; when the recipe is deleted for good, after 7 days, the photo's files go too.
- **Nutrition.** Five optional numbers per serving: kcal, protein, carbs, fat and fibre. A box left empty is "unknown" and is never stored as 0; typing 0 means zero.
- **Ingredient lines.** Up to 200 lines, headings included. Each has an optional amount (200, 1.5, ½, 1½), a unit (g, kg, ml, l, tsp, tbsp, cup, pinch, a plain count, or one of the ingredient's own sizes), the words as typed, a link to an ingredient or to another recipe, and a note. A line with no amount ("salt to taste") is fine and never counts towards stock. A cup is 250 ml. The recipe shows the words you typed; the ingredient's own name appears in small text only when it differs. **Linking (cabledrawer 20 Oct):** "typing never changes my words; only picking from the list links." **A linked line shows the full name (cabledrawer 25 Oct, 0.5.1):** "When a line is linked to an ingredient (automatically or because I chose it), the line shows the ingredient's full name ("thu" → "Toor Dal") in the editor and on the recipe page. Typing alone, with no link, never changes my words (my 20 Oct rule stands for plain typing)." This is option (a) of the 0.5.1 question: words that are only the start of the ingredient's name or of one of its other names ("thu", "E", "pan", "sam") become the ingredient's name ("Toor Dal", "Egg", "Paneer", "Sambar onions"), when picking in the editor and for lines saved before 0.5.1; words typed in full stay as typed ("fresh coriander", "the podi", "thuvaram paruppu"), with the ingredient's own name in small text. A line linked to another recipe keeps its words. The drop-down pick-list stays in 0.6 (cabledrawer 25 Oct). **Line order:** Ingredient, Amount, Unit, Note (cabledrawer 22 Oct; F36, done in 0.7).
- **Steps.** Up to 100 steps, headings included, each up to 5,000 characters, plain text.
- **Tags.** Free tags the household makes up, with suggestions from tags already in use. At most 20 tags on a recipe and 40 characters in a tag (cabledrawer 19 Oct). A tag no recipe has any more stops showing. There is no tag screen in 0.4.
- **Recipes inside recipes.** Any depth; only loops are refused, and the message names the chain ("Sambar powder can't use Sambar, because Sambar uses Sambar powder", and with "which uses" for longer chains). A recipe can't use itself. The server checks on every save. In the editor, a recipe that would make a loop is greyed out with the reason.
- **Made ahead.** A recipe can be marked "Made ahead (keeps in the pantry)". On save, that adds a matching ingredient (the name starts as the recipe's name) and links it to the recipe. Switching it off later keeps the ingredient but unlinks it from the recipe. **Switching it on again (cabledrawer 19 Oct):** with the same name, the ingredient that was kept is linked back to the recipe, with any pantry stock it still has, as long as no other recipe has it as its own made-ahead ingredient; if another recipe does, saving is refused ("There's already an ingredient called …"). **Removing it (cabledrawer 19 Oct):** while Made ahead is on, its ingredient can't be removed from Ingredients until Made ahead is off in that recipe, and Ingredients says why: "Made by the recipe Dosa batter. Turn off Made ahead there to remove it." (with the recipe's real name, and the recipe name a link to it).
- **Editing is all at once.** Nothing changes until Save, and the recipe is saved whole. Recipes are online only in 0.4, like Pantry. Every save adds 1 to the recipe's version number. If two people edit the same recipe, the second Save is stopped and says who changed it ("Wren changed this recipe after you opened it"); the person can look at Wren's version in a sheet over the editor (not a new tab: the installed app has no tabs; closing the sheet brings them back to their own edit, untouched), or choose "Save mine anyway", which saves over it. If a third person saved in between, "Save mine anyway" is refused again, naming them (cabledrawer 19 Oct).
- **Links changed behind an open editor (lead's note, not decided by cabledrawer).** A merge, a removal, a delete or an Undo of those that changes a recipe's links also counts as a change to that recipe (its version goes up, and it names whoever did it; the daily clean-up shows as Mealwright), so an editor that was open is stopped the same way instead of saving old links back.
- **Cancel and offline.** Cancel with unsaved changes closes at once with a "Changes not saved" toast and Undo, which reopens the editor exactly as it was; there is no "Are you sure?". Editing while offline: the editor stays open with everything typed, Save is greyed out, and the note says "You’re offline. Save when you’re back online." What was typed is kept only while the page stays open. **A recipe deleted while it is being edited (cabledrawer 20 Oct):** Save says "That recipe isn't here any more." (under the photo when a new photo is waiting), "as long as nothing typed is lost and the unsaved photo is released": the editor stays open with everything typed, and Cancel deletes the unsaved upload.
- **Deleting.** A recipe goes at once, with no question, and can be undone for 7 days, like a removed ingredient. A recipe used inside another one can be deleted: the other recipe keeps the line's words, marked "recipe removed", and Undo puts the link back.
- **Ingredients that recipes use.** Merging two ingredients moves the recipe lines to the one you keep, and "made its own ingredient again" puts them back. Removing an ingredient keeps each line's words but unlinks it ("not linked"), and Undo links it again. Ingredients says "Used in N recipes", and has the "Not in any recipe" filter.
- **Names and text.** Tabs, line breaks (except in method steps) and other invisible control characters are refused in recipe text, tags and every other name, new or old, so one name can't hide behind another.
- **Stock hints in the All recipes list (cabledrawer 19 and 20 Oct).** An ingredient is in stock when the pantry holds enough for the recipe at its own servings, if the two amounts can be compared; if they can't, any stock counts (cabledrawer 19 Oct, question 22). Stock in every place counts, the freezer too (cabledrawer 20 Oct). A line with no amount never counts towards stock (cabledrawer 19 Oct, question 13), and headings don't count (cabledrawer 20 Oct); a recipe where no line counts gets no stock hint and isn't in "Can cook now" (cabledrawer 20 Oct). A line that uses a made-ahead recipe is checked against that recipe's own pantry ingredient (cabledrawer 20 Oct). A recipe that uses another recipe that isn't made ahead can't be checked until inner recipes are checked, in a later version: it is left out of "Can cook now", its hint never says "all in stock" or "all in stock but 1", and it says "N missing" when something that was checked is missing and no stock words otherwise (cabledrawer 20 Oct). The same goes for a line that uses a made-ahead recipe with no pantry ingredient yet, and for a line that uses a recipe that has since been deleted (cabledrawer 20 Oct). A line with no amount is ignored, whatever it points at (cabledrawer 20 Oct, question 13). The "Uses spinach" line names what the recipe uses that is about to go off, within the Use soon window, with "(today)", "(tomorrow)" or the weekday ("Uses spinach and 2 more (Mon)"), and leaves "all in stock" out beside it (cabledrawer 20 Oct).
- **Stock marks on the recipe page (cabledrawer 19 Oct, question 22).** They follow the servings chosen with − / +: an ingredient is in stock when the pantry holds enough for the recipe at the chosen servings, if the two amounts can be compared; if they can't, any stock counts. Otherwise the page uses the same rules as the All recipes list above.
- **Scaling is "roughly right" (written down in 0.9.5; proposed, for cabledrawer).** The − / + buttons on a recipe multiply every amount by the servings now over the recipe's own, on screen only; the saved recipe never changes. What that does not promise: (1) amounts are rounded to what a person can measure, so a scaled amount can be a little off the exact sum: grams and millilitres to a whole number (never below 1), spoons and cups to a quarter (never below ¼), counts, pinches and packets to a half (never below ½), kilograms and litres to two decimals, or to quarters when the amount was typed as a fraction; (2) every change starts again from the recipe's own amounts, so rounding never builds up from one press to the next, and the recipe's own servings always show the amounts exactly as typed; (3) only amounts scale: cooking times, oven temperatures, pan sizes and the wording of the method steps stay as written, and salt, spices and raising agents often don't scale in a straight line, so taste and adjust; (4) a recipe with Makes but no Serves scales in whole multiples (1× to 99×) and shows no stock marks from 2× up, because the server only works stock out by servings; (5) the stock marks work out the need at the chosen servings and round it up, so a short pantry is never called enough, and where the pantry amount and the recipe amount can't be compared (a cup with no known weight) any stock counts as enough (the rule above).
- **A key sent again with another body is refused (0.9.5; proposed, for cabledrawer).** A change's `Idempotency-Key` marks one change. Sent again with the same body it is a retry and answers as the first did; sent again with a different body it is the app's mistake, so the server answers `409 key_reused` ("That change ID was already used for something else.") and applies nothing. The answers to an "ask once" question are not part of that comparison (a retry may leave them out). Changes made before 0.9.5 carry no body mark and are checked as before. Details: `docs/dev/api-endpoints.md` section 1.2.

## 7. Security and privacy (main decisions settled 17 Oct)

**Built in (enforces the ethos):**

- **One outbound gate:** every outgoing connection passes through one place in the code, which checks the Privacy switches; anything not switched on is blocked. An automatic test fails if any other code makes a network call. Library telemetry is disabled.
  - **Runtime guard (cabledrawer 17 Oct):** the running app also refuses, not just the tests: while Mealwright runs, any network connection, UDP send or DNS lookup made outside the gate is blocked, whether it comes from our code or a library (a Python audit hook in `mealwright.network_guard`, switched on by the server and by the page-reading process; cabledrawer 24 Oct, question 29: "yes, the network guard lives in mealwright.network_guard, switched on by the server and by the page-reading process; change the spec's words to say so"; `mealwright.outbound` still offers it). Local sockets, IP literals and localhost lookups are allowed. Writes on a connection that already exists (a reply going out) aren't new connections and aren't blocked; a UDP send with an address still is (cabledrawer 28 Oct, F22). A reverse lookup (`getnameinfo`) is refused whatever the address, since even a loopback address can ask the system's DNS server (cabledrawer 30 Oct: "reverse lookups refused for every address including the machine's own: yes"), and a test checks that normal requests still work over a real, non-loopback connection (cabledrawer 29 Oct: "Block reverse lookups (getnameinfo) outside the gate, in T: yes, with a test that normal requests still work over a real (non-loopback) connection"). Limit: it only sees networking done through Python's socket module, so a C library with its own networking isn't covered (relevant if the Postgres option arrives: its database address would need allowing).
  - **User agent (cabledrawer 17 Oct):** every request through the gate says it comes from `Mealwright`, with no version number and nothing about the install. This is what "generic user-agent" means for the update check below. Revisit if recipe sites block it in 0.5.
  - **Libraries that make their own connections (designed 17 Oct, before 0.8):** Apprise (notifications) and Authlib (single sign-on) open connections themselves, through `requests`, `httpx` or `smtplib`, rather than through the gate's own request function. They're let through like this:
    1. Each library is imported in one integration module only (e.g. `mealwright/notify.py`, `mealwright/sso.py`), and the import-check test lists them next to the networking modules, so no other code can call them.
    2. The integration module calls the library only inside a gate context, e.g. `with gate.library_call(household_id, Connection.NOTIFICATIONS, hosts=...)`. The gate checks the Privacy switch first. If it's off, or nothing is configured, the library isn't called at all.
    3. The context lets through only DNS lookups and connections for the destinations the household configured: the hosts in its Apprise target URLs, or its identity provider's issuer and the endpoints its discovery document lists. Anything else the library tries (another host, its own update check or telemetry) is still refused.
    4. The allowance lasts for that one call, in that thread only (it's carried by a context variable). Work a library hands to its own background threads doesn't inherit it and is refused, so integrations call libraries in a way that keeps the work in the calling thread. This needs checking for Apprise, which can send to several targets in parallel.
    5. Integrations set the library's user agent to `Mealwright` where the library allows it, so no library or Python version is sent.
    6. Each integration gets tests: with the switch off, nothing is sent; with it on, only the configured host is contacted, and a connection to any other host is refused.
    7. **Private addresses (cabledrawer 17 Oct):** notification targets and the identity provider may be on the LAN (e.g. ntfy, Authelia), but only hosts the admin has put on the same allow list used for recipe import (Settings → Outside connections → Your own network). Any other private, internal or loopback address is refused, as for recipe import.
- **Strict browser rules (Content Security Policy):** pages may only load files from the household's own server, so no CDN or tracker can be added by accident.
- **Logins:** Argon2 password hashing, slow-down after repeated wrong guesses, secure session cookies, no default admin password (the first person to set up creates the admin).
- **HTTPS is required (cabledrawer 17 Oct).** Mealwright is meant to sit behind the household's own reverse proxy, any of them (Caddy, Traefik, nginx, Nginx Proxy Manager…), which provides HTTPS. Browsers only allow these over HTTPS: signing in from other devices (the session cookie is HTTPS-only), installing the app (PWA), offline shopping (service worker) and keep-screen-awake (Wake Lock). On a plain `http://` address, sign-in is refused with a plain-English message saying HTTPS is needed, rather than failing silently. `localhost` counts as secure. For testing on a trusted network, the admin can set `MEALWRIGHT_ALLOW_PLAIN_HTTP=true`: sign-in then works over plain HTTP, the web app shows a warning, and a warning is logged at start-up.
- **Reverse proxy addresses (cabledrawer 17 Oct):** the visitor's real address (for the sign-in slow-down and the sign-in log) comes from the proxy's `X-Forwarded-For` header, believed only from the proxies listed in `MEALWRIGHT_TRUSTED_PROXIES` (addresses or networks). It's empty, so off, by default. The visitor's address is the last one a trusted proxy added, so a made-up header from a visitor doesn't count. The slow-down counts wrong guesses per account and per real address, so one person's guesses never slow down everyone.
- **Secrets encrypted on the server:** notification links (Apprise URLs carry tokens) and the SSO client secret.

**Decided (cabledrawer 17 Oct):**

- **Recipe links on your own network:** imports from private and internal addresses (router, other homelab services, the server itself) are blocked by default to prevent SSRF; the admin can add an allow list (e.g. a home wiki). **0.5 (cabledrawer 21 and 22 Oct):** the checks run after the address is looked up and again on every redirect; entries are a host name, one address or a range; `localhost` and cloud "metadata" addresses stay blocked even if listed; the list is stored with the household and becomes a server-level setting if several households per install ever arrive. See section 6, "Recipe import, decided for 0.5".
- **One answer for a member when a link can't be opened (cabledrawer 18 Nov, Q10):** a member who imports a recipe page, or whose review fetches its photo, is told the same thing, with the same status, code and message, whether the link was refused as a private address, the name wasn't found, the connection was refused, the site was too slow or the secure connection failed ("can't reach" and "can't open the link" are one message), so no member can probe the home network by the answer. The cause stays in the local log only. An admin keeps the reasons (they can change the Privacy settings they point to). (Proposed, for cabledrawer: the one answer is for members only, and an admin keeps each reason. What a member can still tell apart is left as it is: the other reasons for an address an admin has listed on the Privacy screen, and how long a refusal takes. To decide before 1.0.)
- **Signing out on a phone** wipes that device's offline copy (shopping list, cached recipes, waiting changes), with a warning first if changes haven't been sent yet.
- **Export everything** offers an optional password that encrypts the file; it is offered but not required.
- **What the export leaves out (cabledrawer 12 Nov; the rest cabledrawer 13 Nov):** sign-ins and sign-in links and passwords; API tokens and the single sign-on client secret; also this server's mark of a login the sign-in server refused, and the old names kept for Report a problem. Whoever restores from an export sets passwords again. The format is in `docs/export-format.md`. The optional password is built (0.9.5; cabledrawer 13 Nov): `POST /api/v1/export` with the password in the body sends the file encrypted, as described in `docs/export-format.md`.

**Decided after the 0.4 security audit (cabledrawer 19 Oct, "Accept all six"):**

- **HTTPS only, remembered by the browser (HSTS), done in 0.4:** in https mode (the default) every answer tells the browser to use only https for this address for a year (`Strict-Transport-Security: max-age=31536000`). No `includeSubDomains` and no `preload`, so other sub-domains are not affected; another plain-http service on the same host name (a different port) would be. Never sent in plain-http mode (`MEALWRIGHT_ALLOW_PLAIN_HTTP`).
- **Longest sign-in, done in 0.4:** a sign-in without "Remember this phone/computer" still ends after 12 hours without use, and now also ends 30 days after it started however often it's used, the same as with it.
- **Shortest password, 0.9:** 12 characters for new passwords (set up, password change, reset). Existing shorter passwords keep working.
- **No leaked-password list (cabledrawer 11 Nov; replaces the 19 Oct line "new passwords are checked against a list of leaked passwords bundled with the app"):** no bundled leaked-password check. New passwords need 12 characters, together with the per-username lock-out and the limit on Argon2.
- **`__Host-` cookie name, 0.9:** the sign-in cookie gets the `__Host-` name, so a site on another subdomain can't set it. It signs everyone out once. **Plain-http mode (cabledrawer 11 Nov):** it keeps today's cookie name and the sign-in page shows a "not secure, this device only" note; https gets `__Host-`.
- **New-password window, timing (cabledrawer 12 Nov, "accepted"):** for 10 minutes after reset-admin or a password change, a paused real username takes a password check (about 50 ms) and a made-up one doesn't, so a guesser can tell the name is real and its password is new. Accepted, not hidden: hiding it would show the opposite difference outside the window and cost a password check for every paused guess. The window itself, the known-device cookie and the waiting room of 4 are proposed, for cabledrawer (0.9 A2).
- **Database file readable only by Mealwright, 0.9:** `mealwright.db` (today readable by any user inside the container) becomes readable only by the `mealwright` user, done with the backup docs (lead's note: once it's clear how backup tools read `/data`).

**Backups (cabledrawer 17 Oct):** the app makes its own backup automatically, daily by default, into its existing data volume, keeping the last 7. The user can change how often and how many are kept. Nothing leaves the server; the user's own backup tools can copy it from there. **Backups and photos (0.9.5 step 16f, D2; cabledrawer 13 Nov):** every backup and the safety copy before an upgrade include the recipe photos unless an admin switches **Include photos** off (Settings → Your data, on by default, saved as picked, admins only, applied to scheduled backups, Back up now and the safety copy before an upgrade; it changes only the copies made afterwards). **The copy before Delete everything always includes the photos, whatever the switch says (proposed, for cabledrawer; the safest: they would otherwise be gone for good).** A copy `X.db` gets a folder `X-photos` beside it, in the layout of `photos/`, made of hard links to the live files (a photo file is never changed once written, so no photo is copied twice; where a link can't be made the file is copied). Consistent while in use: the photos are linked first, then the database is copied with SQLite's online backup (a read lock only, so no photo is ever copied under the write lock), then the folder is looked at again for photos added meanwhile; the `.db` is put in place last and is what makes a backup count. A full disk fails the backup with one plain line and leaves nothing half-made; the older backups stay. Restore is the database file as before plus `cp -an` of the photo folder into `data/photos`. Without a photo folder (switch off, a backup from before 0.9.5, no photos then) a restore keeps the photos already on the server, and a recipe whose file is missing shows no photo (the photo address answers "not found"; the list shows its plain square, the recipe page shows none; nothing else is affected). (Words proposed, for cabledrawer.)

**API tokens (cabledrawer 17 Oct):** each token is read-only or full access, with an optional expiry date (e.g. a read-only Home Assistant token can see the list but not delete recipes).

**Taking an admin out at the sign-in server (O2 review r3; accepted as built, cabledrawer 12 Nov):** taking an admin out at your sign-in server doesn't stop their API tokens on its own: make them a Member or remove them in Settings → Household. (When single sign-on refuses a known login, its sign-ins and tokens end; the household's last admin who can still sign in by password keeps theirs.) **(O2 review r4; accepted as built, cabledrawer 12 Nov:)** when no other admin can get in without the sign-in server's say (since 0.9.5, #205 (d), a password that works now; a sign-in that hasn't run out is no way in, and being linked is not enough when the sign-in server itself is refusing a login at sign-in (a lasting answer also needs a sign-in open now); proposed, for cabledrawer), the refused admin keeps their sign-ins but loses their tokens, with passwords on or off, so one refusal can't lock the household out.

With passwords off, the hourly check never ends the only admin's last sign-in; Settings shows a warning instead (cabledrawer 12 Nov).

A login the sign-in server has refused is marked (`sso_refused_at`) until it accepts them again; while marked it can't make API tokens and tokens it made after the refusal stop (cabledrawer 12 Nov). The mark ends only when a fresh sign-in is accepted and the groups give them Admin, or an admin makes them a Member or removes them; a working refresh no longer clears it (fix13 review, accepted as built, cabledrawer 12 Nov).

**A kept admin is still a full admin (cabledrawer 12 Nov).** The only admin, kept signed in after the sign-in server refuses them, keeps every admin power, by design, because nobody else can get in. The mark stops the direct route (a refused admin can't simply keep a token that never stops); it doesn't stop an admin using admin powers, for example changing the single sign-on setup or giving someone else an admin login. The real fix is at the sign-in server, or a second admin. Docs advice: to remove someone from Mealwright, first make sure another admin can get in, then remove them in Settings → Household; disabling them only at the sign-in server isn't enough while they're the only admin. Follow-up (0.9.5): Recent changes or the log records what a kept admin does (new tokens, single sign-on setup changes).

**Demoting and the last admin, #205's edge cases (cabledrawer 12 Nov late; built in 0.9.5):** one rule answers "can another admin get in?" on the Settings side (making an admin a Member or a shared login, removing an admin, Undo of those): an admin counts only with a password that works now (password sign-in isn't switched off), or a single sign-on link accepted at the saved sign-in server while single sign-on can start and the sign-in server hasn't refused that login (not marked). A sign-in that is open now, an API token, a sign-in or join link not used yet, and a link not accepted yet are no way in; shared logins and removed people don't count. **What really changed in 0.9.5 (proposed, for cabledrawer):** (b) and the Settings side of (d) were already refused by `admins_left` before it, which never counted a live sign-in; what changed is that a link counts only while single sign-on can start and the admin isn't marked refused, and that the sign-in server's side now follows (d) too. **Where the sign-in server takes an admin out** and the answer lasts (the hourly check's "ended", a demotion by the groups; proposed, for cabledrawer), another admin counts only with a working password (passwords on), or an accepted, unrefused link while single sign-on can start AND a sign-in open right now. So a link while signed out doesn't count and the demotion waits, (c) accepted as built; a live sign-in with no link and no working password doesn't count, (d); a link and a sign-in open now does. Two admins taken out together: the first one's sign-in ends, which stops it counting, so the second is kept: one stays, never none. (b): the server refuses with the usual "…is the household's only admin. Make someone else an admin first." (`last_admin`, 409). **At sign-in** (`_refused_known`: the sign-in server refuses a known login) a link counts for nothing, only a working password, because the same groups that refuse one may refuse the other (O2 r5, accepted as built). Until another admin can get in, `reset-admin` is the way out. Every other "proposed, for cabledrawer" item in #205 (single sign-on and token rules, the stricter mark-clearing rule, one PR for O1 and O2, the docs line) and #208 is accepted as built.

**Logs (cabledrawer 17 Oct):** errors and sign-ins only, never what people cook, buy or type. Kept for 14 days, stored locally, never sent anywhere. **How (0.1.1, cabledrawer asked Claude Code to choose, 17 Oct):** the app keeps its own log file in the data folder (`/data/logs/mealwright.log`, owner-only). A timer starts a new file just after each midnight UTC and deletes files last written more than 14 days ago, so this holds on a quiet server too; "Report a problem" reads recent errors from it. Every line carries a UTC time. **Sign-in lines (anything with a username or address) go only to this file, never to the container output (cabledrawer 17 Oct):** Docker can only limit its copy by size, so on a quiet server it would keep them for months, or years with a large server-wide default. The container output gets start-up messages, warnings and errors; the example compose file still caps it at 2 × 1 MB as a safety net, overriding the server's default. Backups should leave `data/logs` out, or they keep sign-in lines beyond 14 days. **Blocked connections (cabledrawer 17 Oct):** the "Blocked outgoing connection" warning stays in both the container output and the file, but names only the switch in plain words ("recipe import is switched off"), never the host, site or URL: a site name shows what someone was cooking. **Sign-in log lines (cabledrawer 17 Oct):** every sign-in writes "Signed in"; the slow-down is logged once when it starts or doubles, with the wait (not on every refused try, so the log can't be used to fill the disk); a username is logged only if it's a real account, otherwise "unknown user", so a password typed into the username box never reaches the log.

**Bug reports (cabledrawer 17 Oct):** Settings → About has a "Report a problem" button. The server never sends anything; the person does, after seeing exactly what's in it.

1. The app builds a short report on the server: app version, browser and phone type, recent errors from the log, and a "What were you doing?" box.
2. The person sees the whole report first, with personal details already removed (no names, recipes, pantry contents or server address), and can edit or delete any line.
3. They choose how to send it: **Open on GitHub** (a pre-filled new-issue page in their own browser; needs a GitHub account), **Copy**, or **Download as a file**.

**Old names in a report (beta fix5; cabledrawer 12 Nov):** a log line can outlive the name in it, so the names are kept where they are written. A table, `former_name` (household, kind, name, when), is filled by one hook on every database change: when a person, household, recipe, ingredient, tag, shop, place, list or meal changes its name, the old name is kept; when it is deleted, its current name is kept; a bulk delete or update, and rows that go with a parent, are covered too. "Report a problem" removes them like current names, for every household (a log line is server-wide). The nightly log tidy deletes those older than the log files plus a day (15 days), in the same run. They are left out of the export. **Delete everything** takes the household's kept names with it and writes none; the report also leaves out every log line from before the new set-up, and, for any household, every line from before the latest Delete everything of any household (dated by its safety backup, which is never trimmed): another household's report holds no line with a deleted household's names, foods or people; general app lines from after it stay (cabledrawer 12 Nov). **One household's Delete everything and another's report (beta fix6; cabledrawer 12 Nov):** the log is server-wide, so a report leaves out every line from before the latest Delete everything of any household (dated by its safety backup), as well as from before its own set-up; see Bug reports above. The undo data of Recent changes stays as a second net for history older than this change. Nothing here is sent anywhere.

No automatic crash reporting. Not in the Privacy list, because the server makes no connection for it. **Settings mockups:** add "Report a problem" to About.

**Updates (decided, cabledrawer 17 Oct)** — three levels, all built:

1. **No connection, always on:** the app knows its own release date; after a while Settings → About shows "This version is 4 months old. New versions are listed at <link>." Opening the link is the user's own click.
2. **"Check now" button, admins only:** one plain request to GitHub's public release list. Nothing about the user or install is sent (no install ID, no version in the request; the user-agent is just `Mealwright`, with no version, as for every request through the gate); the comparison happens on the server. **Check now always works for an admin when pressed, whatever the daily switch says** (the note beside it says it asks GitHub's release list); the daily switch only controls the automatic check (cabledrawer 12 Nov).
3. **Automatic daily check, off by default:** the same request once a day, listed in Settings → Privacy with its own switch. When an update exists, admins see a small "Update available" badge, optionally also sent through the household's own notifications.

Also: the app reports its version number on the local network (in `/api/v1`), so Diun, Renovate etc. keep working with no extra connection. **Settings mockups need updating** (Privacy gets the update-check switch; About gets the version-age note and Check now) — all four versions.

It starts from the non-goals (section 1), the ethos hard rules and "Not in v1" (section 2), and grows as requests come in. (Why: Actual Budget does this publicly; saying no is the main way a spare-time project stays maintainable.)

Each milestone lead reads it when its milestone starts. The non-technical prototype test runs at 0.9, with the private trial (cabledrawer 19 Oct), instead of before 0.4. (Why: Tandoor's biggest complaint is a dense, hard-to-learn UI, and Mealwright has as many features.)
- **A small private trial at 0.9.** Two or three invited self-hosters install a 0.9 build on their own servers and use it for about a month, alongside the community review. It stays private: no public image or release, so "no public test version" still stands. How they get the build is decided at 0.9.
- **Plan for stepping away.** `docs/dev/` gets an architecture overview (how the pieces fit together) and a "how to build and release" guide, so someone else could carry on or fork cleanly. Written in 0.9 and kept up to date after. (Why: Paperless-ng stalled when its only maintainer went quiet, and contributors had to fork it as Paperless-ngx.)
- **Release slowly after 1.0.** New features are bundled into minor releases about once a month at most; security fixes go out as patch releases whenever they're needed. (Why: Immich released about every five days, but it has a full team.)

## 9. Roadmap and build versions (settled 17 Oct)

CI starts at 1.0 on GitHub Actions, when the code moves to GitHub. **How `./check` runs the scanners (cabledrawer 17 Oct):** pip-audit and Bandit through `uvx`, each pinned to an exact version (and to dependencies published before a fixed date); osv-scanner as a Docker image pinned by digest, with the repo mounted read-only; Trivy as a Docker image pinned by digest, scanning an exported image file with no access to Docker. **Bandit, not Semgrep:** Bandit runs fully offline, while Semgrep downloads its rules from its own registry under a non-open rules licence and sends usage metrics by default. All four are Apache-2.0 and are dev tools only, never part of the app. They send package names and versions to vulnerability databases or download one, and nothing about the install or the homelab. Trivy sends anonymous usage data to Aqua and checks for its own updates by default; both are switched off (`--disable-telemetry --skip-version-check`, 17 Oct). **Fixed test date and time (cabledrawer 21 Oct):** "the screenshot and browser tests run on a fixed date and time, the same for the server's test data and the browser (Playwright's clock), so a check that runs across midnight or a clock change (UK clocks go back on 25 Oct) can't fail this way again." The browser's clock is fixed at 2026-10-17 09:00 UTC. The server is told the same time by a test-only launcher, `backend/scripts/e2e_server.py`, which is not in the image and is off unless the browser tests start it (cabledrawer 21 Oct: "The test-only launcher for the fixed date and time is fine."). **Browser tests (cabledrawer 17 Oct):** Playwright 1.63.0 (Apache-2.0), installed in WSL as a test-only tool in `e2e/`, running headless Chromium against the real app on 127.0.0.1. Its system libraries were installed by cabledrawer (`sudo npx playwright install-deps chromium`). **Trivy rule (cabledrawer 17 Oct):** Trivy fails the check on HIGH or CRITICAL vulnerabilities that already have a fix, and skips ones with no fix yet. **Security fixes skip the age rule (cabledrawer 20 Oct):** libraries and tools are pinned to versions released at least two weeks earlier, but "a version that fixes a published security warning may skip the two-week age rule, if the PR names the warning (ID and severity) and no other library changes." At 1.0.0 the code moves public to GitHub via a Forgejo push mirror; section 8 (GHCR + Docker Hub, GitHub issues and Discussions) applies from then on. **When `./check` runs (cabledrawer 17 Oct, from 0.3):** three levels. While working: only the test file for the change, plus lint and type checks on the side being touched. `./check --fast` after a chunk of work or a round of review fixes: backend and frontend checks and tests, without fresh installs, browser tests, scanners or the image. The full `./check` is still required before opening every pull request, again on the final commit after the last fixes (the pasted summary must match what is merged), for every release pull request, and whenever a dependency, lock file or the Dockerfile changes. The checker accepts a pasted summary whose commit matches the pull request's latest commit instead of running it again; it runs the screenshot review and that feature's browser tests. Nothing is skipped silently: a pull request without a full pass on its final commit isn't ready.

**Test bed and where Claude Code runs (cabledrawer 28 Oct):** 0.x builds are installed and hand-tested on a test VM, not on the code server's machine (Forgejo stays where it is). Claude Code stays on WSL (cabledrawer 28 Oct: "let it run on wsl"); the move to the test VM's machine is on hold. The machine names are in `CLAUDE.local.md` (git-ignored).

**Postgres (cabledrawer 28 Oct):** the recipes and plan migrations give Boolean columns `server_default=sa.text("1")`, which works on SQLite but breaks on Postgres. The old migrations are left as they are (cabledrawer 28 Oct: "leave the old migrations"); a Postgres version would have to fix it, and new migrations use `sa.true()` / `sa.false()`.

**Working lessons from 0.3 (cabledrawer 18 Oct):** (1) Long design docs get a one-page summary at the top with section numbers; helpers read the summary and only the sections their pull request needs, never the whole file. (2) When cabledrawer makes a decision that affects a pull request, the lead copies it word for word into `docs/dev/progress.md` under that pull request, and the checker checks the pull request against that list. (3) All of a milestone's product questions go to cabledrawer before its first code pull request starts. (4) Two pull requests run side by side only when they touch separate parts of the app; ones that share behaviour run one after the other. (5) The mockups canvas is kept up to date only for screens not built yet, and a mockup is changed before its pull request starts, never after. Once a screen is merged, the app and its pull request screenshots show how it looks.

**Faster working (cabledrawer 18 Oct, from 0.4; added to 19 Oct):** (1) The lead is on Opus at the usual effort, and cabledrawer only talks to the lead (cabledrawer 19 Oct; the model part replaced by "Working method from 0.8", cabledrawer 6 Nov). A fresh helper is started for each pull request, in its own worktree, and closed when the pull request merges (cabledrawer 19 Oct). Pull requests run side by side when they touch separate parts of the app; ones that share behaviour run one after the other (as in lesson 4 above). (2) Merge order: whichever pull request is ready first goes first; the other is then moved on top of the new `main`, and its full `./check` is run again on its final commit before cabledrawer merges. (3) Up to three helpers at once, but at most two builders; the third slot is only for a checker, so a risky pull request's checker never waits for another builder. If cabledrawer says usage is near its limits, go back to two helpers. (4) Two review levels, and the pull request description says which one it got. **Light** (paper cuts, wording, docs, low-risk screens): one checker pass on the final commit, by Sonnet; if it finds something, the fixer fixes it and the checker checks only those fixes. **Full** (sync, offline, sign-in, households, permissions, imports, uploads including recipe photos, the outbound gate, security, database changes): as in 0.3, and the verdict also has a Security section (spec section 8, "Security along the way") (cabledrawer 19 Oct). A full `./check` on the final commit before merge applies to both. (5) Every full `./check` runs one at a time through a shared lock file (the lead names its path), because the vulnerability scanner keeps one shared cache that two runs at once can break. `./check --fast` and single test files can run side by side. (6) Each worktree uses its own `CHECK_IMAGE` name and `E2E_APP_PORT`, so two runs never share an image name or a browser-test port; each run also has its own `.check/` folder and empty data folders. (7) Which model does what (cabledrawer 19 Oct): Opus at high effort for the security audit and its review, and for any builder or checker on a full-review pull request that touches sign-in, households, sync or uploads; Sonnet for everything else. If usage gets tight, the lead tells cabledrawer, and we go back to two helpers first. (8) Helpers only ever stop their own runs (their own `./check`, test server or command), by their own process, and never with a broad command that could hit another helper's work. Overnight on 19 Oct a broad stop killed another helper's full `./check`, so every helper brief repeats this rule (cabledrawer 19 Oct). (9) Helpers report back in 10 lines or fewer, and read only the spec sections their brief names (cabledrawer 19 Oct). (10) Branch protection is on (cabledrawer 19 Oct): `main` changes only through a pull request that cabledrawer merges. Pushes to `main` are switched off for everyone, administrators included, and only `tess` can merge. A local pre-commit check refuses commits made on `main`. Nobody changes or bypasses either one.

**Working pace (cabledrawer 18 Oct):** all of a milestone's questions in one sitting at its start, pull requests side by side when they don't overlap, light review for low-risk pull requests. Not cut: the security audit, the full `./check` before every merge, and the two-device and household tests.

## Data model notes collected so far (for step 6)

- A meal = (date, slot) container holding one or more items; an item is a recipe (fresh), a tub from a batch cook, or a plain food ("Fruit"). Meal nutrition = sum of items.
- Slots are per-household configurable: name, order, on/off (defaults Breakfast, Lunch, Snack, Dinner). Hiding a slot keeps its meals.
- Batch cook = recipe + cook date + portion count + spread pattern (lunches / lunch & dinner / dinners / manual); tubs link back to it, each optionally assigned to a household member and placed in a meal, in the freezer, or unplaced ("tubs left").
- Cook-day prep notes ("soak chickpeas the night before").
- Food: name, aliases, default location, tracking mode (weight / volume / count / staple), grams-per-cup (optional), per-item weight (optional), pack size (optional), running-low level (optional), preferred shop (optional). Household-learned conversions (from "ask once", when "remember" is on) stored on the food.
- Recipe ingredient: food link, amount in base unit, original text (as written), note ("peeled").
- Stock lot: food, amount (base unit), location, expiry (optional), added date — deductions take the soonest-expiring lot first.
- Locations: per-household list (defaults Fridge, Freezer, Cupboard, Spice rack), renameable.
- Shops: per-household list of names, with aisle/category order.
- Stock change log (cooked / shopped / adjusted / moved / binned, who, when) — powers Recent changes and Undo.
- "Cooked it" confirmation records per-ingredient include/exclude and used-or-left overrides.
- Per-user settings include units display (metric / as written; cups after 1.0), theme (auto/light/dark), sidebar collapsed state, keep screen awake in Cook mode.
- Household settings include outside-connection switches (recipe link import, photo download), notification targets, staples check on/off, use freezer stock last.
