# Changelog

All notable changes to Mealwright are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Version numbers follow the plan in `docs/spec.md` section 8: 0.N.0 per build milestone (not published), then MAJOR.MINOR.PATCH from 1.0.0.

## [Unreleased]

### Changed

- Unticking a line in the trolley joins it back into the line still to buy for the same ingredient, list and shop, so there is one row to buy instead of two (L1c, Sh7). Undo of the untick puts both lines back exactly as they were while the line it joined is unchanged; otherwise the unticked line comes back on its own and nothing needed is lost. The phone shows the join at once, offline too. Lines counted in different sizes are not joined.

### Fixed

- On a phone, a Pantry that holds only leftover tubs shows them in their place instead of "Nothing in the pantry yet" (found while taking the 0.9 screenshots).
- A person made at first single sign-on sign-in with a long name is cut at 100 characters like any other name (never in the middle of a flag), and when "Name (username)" is taken too, a number is added: "Name (username) 2".
- "Delete everything" forgets the wrong-password counts of the deleted household's people only; the counts of another household on the same install stay.
- The hourly sign-in check ignores an answer from the sign-in server when the single sign-on settings (the issuer or the client) were changed while the server was being asked, so an answer meant for the old setup can no longer sign people out, stop their API tokens or seal a new token for it.
- Your data: Export is switched off while the device is offline, like the page's other buttons, instead of giving the browser's own failed download (L11).
- API tokens, for someone who can't see the list (a member who opens its address) or while it loads: the words are no longer on the card's left edge (L10).
- Single sign-on setup: Copy says "Couldn't copy. Select the address and copy it." when the browser has no clipboard (before, nothing at all; the words are proposed, for cabledrawer), and the form is loaded once, so narrowing the window and widening it again no longer replaces what was typed (L8 and L13).
- A login made by single sign-on is no longer offered "Change password": Settings → Sign-in leaves the row out, and the page, if opened, says "This login has no password to change: it signs in with single sign-on." instead of asking for a current password (L7).
- API tokens: "Delete" and the form's error lines are readable in the dark theme (they were red on dark, 3.3 to 1; now the lighter red used elsewhere). Set-up's problem lines, which were white and so invisible in the light theme, use the same red (L6, found in the sweep).
- The back link "‹ Sign-in" on Change password, API tokens and Single sign-on lands on the Sign-in section of Settings, not the top of the Settings list (L5).
- Set-up no longer throws away a name or shop that was typed but not added: Next, Skip and Finish setup add it first. If it can't be added, the step says why and stays (whole-0.9 review, M3).
- Undo of a removed place puts its stocktake answers back only into the stocktake they came from, in every order of events: "Start a new stocktake" marks the removals that can still be undone as from an earlier stocktake. Before, a few orders left the old answers out, and a restart with nothing answered since could bring them into the new stocktake (L1c). Removals made before this version keep the earlier check.
- A tick on an ingredient with no pack size kept none of a line that had grown since the phone showed it: the whole line was ticked for the amount the phone showed. The rest now stays to buy, as it already did for an ingredient with a pack size (found while building Sh7).
- **Plan this batch (F229, cabledrawer 12 Nov).** The second and later recipes' "Where the tubs land" shows the tubs the earlier recipes already placed, as "Paneer Butter Masala · Tub 1 · already placed", so a meal that is taken doesn't look free. "Already placed" is proposed, for cabledrawer. The server's count ("N of M placed") and where the rest go were already worked out after the earlier recipes; only the grid hid them.
- **Use a tub (F230, cabledrawer 12 Nov).** A tub is never offered for a meal on a day before its batch's cook day, nor, on the cook day, for a meal at or before the cooking (spec F50). The Plan's list leaves them out, and the server refuses such a placement or move (422, "Pick a meal after the cooking, today or later."; proposed, for cabledrawer). A tub may still go to a past day, as before.
- **The Pantry's Fridge (F230, cabledrawer 12 Nov).** The tubs of a Batch cook session are listed (and counted, and in Use soon) only after that session's Cooked it. A Cook once batch outside a session is listed as before.
- **Today after Cooked it (F233, cabledrawer 12 Nov).** Once a Batch cook session's Cooked it is done, its cook-day meal's kcal and name count only what is eaten there (a tub eaten at that meal), not the recipes the session cooked. A meal with nothing else in it still counts them. The Plan's meal line ("1 thing · 400 kcal each") counts the same way, while the names on the Plan's cards still show everything cooked there (F233, Plan; proposed, for cabledrawer).
- **The Plan card (F234, cabledrawer 12 Nov).** Once batch cook mode has been started for a session (even after every recipe is cooked), the card's button says **Carry on batch cook** (proposed, for cabledrawer) instead of "Start batch cook". The Plan asks the server for the session's schedule to know; offline it keeps "Start batch cook".
- **Use a tub, cooked ahead (L1, whole-0.9 review).** A Batch cook session (or a Cook once batch) that you cooked before its planned day has its tubs offered from the day it was really cooked, not only after the planned cooking meal. Before, those tubs could not go in any meal for days, and the last fridge day was lost. The Plan's tub list and the server now agree on that day.
- **Shopping, an untick beside the plan's own line (L2, whole-0.9 review).** Taking back a tick, when the plan has since made a second line for the same ingredient, joins the two lines into one that the plan still keeps up to date: a meal planned afterwards is bought for. Before, the joined line was treated as typed by hand and stopped following the plan. A line you typed that joins a plan line still counts as a hand edit.
- **Shopping, a phone that is behind (L3, whole-0.9 review).** When one phone takes back a tick and the bought row joins into the line still to buy, a second phone that had not heard yet and takes that old row off (or changes its amount) now touches only that row's own part of the joined line; the rest stays to buy. Before, the whole joined line went, with no note. An Undo of it puts the amount back.
- **Eat a tub of a meal cooked ahead (H, whole-0.9 review).** When you press Cooked it on a meal before its planned day and keep leftovers (with or without checking the pantry), the tubs now count from the day you really cooked it, so they can go to a meal on any day after that, as the Plan and Use a tub already said. Before, the tubs were refused until after the planned day, and "Eat it on…" in "Any left over?" could miss its tub. The same holds for the tub where you first chose "Leftovers on…" and then pressed Cooked it early: it can go to a meal from the day after you cooked (its use-by date is not moved). A tub of a recipe you have not cooked yet stays put when you cook only another recipe of the meal ahead.
- **Shopping, a phone that is behind, again (L3, whole-0.9 review).** The bought row's share of the joined line is now kept, so a second stale change from the same phone, or a stale delete after a stale amount change, or a second phone's delete, no longer takes the row's amount off the line twice. A stale delete of a row that joined a line to buy with no amount puts that line back to no amount, instead of taking it off the list. An Undo gives the share back.
- **Guessed step timings, "or" (L4, whole-0.9 review).** An "or" now counts as a choice between two ways only when a time follows it directly ("12 hours in the oven, or the yogurt setting 8 hours"). "Add garlic or ginger and fry 2 minutes" and "turning once or twice, and rest 10 minutes" add their times up again, so Batch cook no longer plans too little time for such steps.
- **Guessed step timings, instant pot (L5, whole-0.9 review).** "Instant pot slow cook for 4 hours" is the cooker and waiting, and "in the instant pot sauté the onions" is the cooker and hands-on. A step that sautés and then waits ("saute the onions for 5 minutes, then slow cook for 4 hours") is waiting, not hands-on. Only the steel insert, liner or inner pot (without a cooking word) and the yogurt setting still name no appliance.
- **Batch cook (F227):** Start timer, Skip wait and End timer on each recipe of the session sit in one row of same-size buttons, which stays in the row on a phone.
- **Start times (F228):** a recipe whose saved Time already includes its wait (Dosa Batter: 745 min with an 8–12 h ferment) no longer counts the wait again as work: its work is 25 min, not 12 h 25 min, so "When will you start it?" offers starts that are ready by the meal, and Today's work time follows. The sheet says so, with the earliest ready time, when the start you pick (offered or Another time) can't be ready by the meal. The rule is proposed, for cabledrawer (spec, "The plan works backwards"). `GET /plan/start-options` gains `active_minutes`.
- **Guessed step timings (F231):** "8 hours" and "12 hours or the yogurt setting 8 hours" give the longer way, not the two added up; moving the batter to a bowl or an instant pot steel insert is hands-on, not a wait; an instant pot insert or the yogurt setting no longer names the pressure cooker.
- **Batch cook, late replies (L1d).** A slow reply from the server no longer overwrites a newer copy of the schedule on the Batch cook page: an older ask is dropped when a later one (or a mark on this phone) has happened since. The page also waits a moment after another person's change and asks once, like the Plan page.
- **Batch cook, opening and Plan again (L1d).** A slow open of the Batch cook page, or a slow Plan again, no longer overwrites a newer copy of the schedule (a refresh, or a mark on this phone, made meanwhile): the older reply is dropped.
- **Test tidy (L1d).** The Batch cook test that checks an Optional step doesn't change the schedule's basis uses a real hands value instead of a type ignore.
- **Import, "or more" endings (L1d).** "1 tsp salt or more-to taste" (no space before the dash) no longer offers an ingredient called "more": it reads as salt with "or more, to taste" in the note. "1 tbsp oil + more for frying" (also "+ extra", "plus more") is one line, oil, with "+ more for frying" in the note, instead of a second ingredient "more".
- **Undo of the pint and of the Batch cook switch (L1d).** An Undo of a pint change, or of switching Batch cook on or off, is now refused ("That can't be undone: the pint has been changed again." / "…Batch cook has been switched again.", the words already used) when the same setting was changed again after it and that change still stands, even if the value is the same as it was (UK, US, UK). Before, only the value was compared. A later change that was itself undone doesn't count.
- **Meal slots, retries (L1d).** A retried "add a meal" with the same Idempotency-Key now answers what the first one did (the new meal) instead of 409 `slot_exists`; no second meal is made. A rename plus hide sent with a key answers a retry with the last change made, as the first answer did (it was the rename's before). A no-op rename kept by its key still answers (not 404) when the meal is gone at the retry (it already did; a test now holds it), and a retried save that changes several fields has its test.
- **Drafts list, faster (L1d).** The Drafts list reads the household's ingredients (and where they are kept) once per request, not once for each draft that has waiting lines.
- **Delete everything forgets what was only in memory (whole-0.9 S3, D1).** The last single sign-on test result (it names a person, their e-mail and groups), a test's waiting link, the proof that a setup works, the "kept signed in" warning, the last update-check answer and the counts of wrong passwords for people, devices and password changes are all emptied, so whoever sets Mealwright up next never sees the old household's. Counts of wrong guesses by address stay.
- **Names from the sign-in server (whole-0.9 S4).** The name the sign-in server sends for a new person is tidied as a typed one is (line breaks, hidden and text-direction characters out), also in the setup screen's test result. When someone in the household already has that name, the new person is "Name (username)" instead of a second person with the same name.
- **Report a problem hides more (whole-0.9 S6).** The report's cleaning also removes the names of API tokens, the names of single sign-on groups (as "[removed]") and the sign-in server's address (as "[server]") from the log lines it shows. A token's old name is kept for that, after it is renamed or deleted, as other names are.
- **Settings → Household, single sign-on people (whole-0.9 Pe4).** A person who signs in with single sign-on reads "Member · signs in", as a password login does, not "sign-in link sent"; their page no longer says the link has run out (with buttons the server refuses) and shows the Shared login switch. `GET /people` gives each login `signs_in` (password or single sign-on).
- **"Who's this?" while the tablet is in use (whole-0.9 Pe5).** Any request from the tablet keeps the pick going, not only a saved change: after reading a recipe or the plan for half an hour, "Cooked it" is still recorded for the person picked, not for "Kitchen tablet". A pick that has already run out is not brought back by reading.
- **Settings → Household, a person's page (whole-0.9 Pe10).** A person nobody is recorded as having added (the first admin, and logins from before 0.9 or made by single sign-on) reads "Added 3 Nov", not "Added 3 Nov by" with nothing after it.
- **The hourly single sign-on check (whole-0.9 S1, S2).** The check no longer keeps the database busy while it waits for the sign-in server, so a slow sign-in server doesn't make other saves wait. Each person's answer is saved as soon as it comes: if Mealwright stops half-way, the people already checked keep their new refresh tokens and are not signed out at the next check.

## [0.9.0-beta.1] - 2026-11-12

The first 0.9.0 test version (alpha.1 was not released; its changes are here too, under "People and roles (0.9 A1)" and "Security (0.9 A2, sign-in hardening)"): the household's people and their roles (A1) and harder sign-in (A2), plus Settings in the spec's order and Licences and credits (U1), onboarding and "Amounts shown" (U2), backups, export, restore and Delete everything (D1), a hardened data folder and compose example (D2), the update check and About's update parts (X1), Report a problem (X2), the install guide and proxy examples (M1), single sign-on (O1), API tokens (O2), the leaving-a-page fixes (T1), the pool fix, and Report a problem's old names. Several lines are marked "proposed, for cabledrawer": they are words or rules I chose that still need your yes.

From alpha.1 (built, not released; 0.9's words agreed by cabledrawer, K0): people of the household with or without a login, shared logins for a kitchen tablet, "Who's this?", one-time sign-in links an Admin can give a Member; sign-in that counts every try before the slow password check, a waiting room for checks, a 12-character rule for new passwords, known devices that a guesser can't lock out, and a ten-minute window after a new password (cabledrawer 12 Nov). Over https the sign-in cookie is now `__Host-` only, so **everyone signs in once more** after updating; plain http keeps today's cookie and shows a "not secure" note.

**Before you install it: back up your data.** This version changes the database eight times since 0.8.0 (people `b4e8c2a6d917`; the device a sign-in came from and the date of each password `b4f8e2a6c917`; backup settings `b2f7c4e8a915`; onboarding and amounts choice `c7a1e5d3f802`; single sign-on `c1d5e9a3f702`; API tokens `c3a7e5d1f824`; a mark on a login the sign-in server refused `e5b3c9a1d742`; the old names kept for Report a problem `d3a9f1c7e254`), and the old version can't read a database the new one has changed. The steps are the same as before (`docs/dev/test-on-homelab.md`, section 4.1): stop the app, make a dated copy of the `data` folder in `backups/` with the old version's number in its name (it leaves out the logs), check it is there and not tiny. `data/secret.key` (single sign-on's key, made the first time it is needed) is inside that copy; if you back up some other way, take it too. To go back, follow section 5 of the same file (restore that backup with the 0.8.0 image; anything changed after the update is lost).

### Added

- **Your data (D1; proposed, for cabledrawer).** Settings › Your data: Mealwright backs its database up by itself into `data/backups/`, daily at 03:00 by default and keeping the last 7 (an admin picks daily, twice a day or weekly, and 1 to 30 kept), with Back up now, the last backup and any problem in plain words. A backup never replaces another. **Export everything** is one streamed zip of the household's tables and photos (admins; no password on the file yet). **How to restore** is a page and `docs/restore.md`, proved by a script that restores a backup into a fresh container and signs in. **Delete everything** (admins) asks for typed words and the password, makes a safety backup first, keeps the backups folder, signs everyone out and starts first-run setup again, printing a new setup code in the log. Members see the screen but can't change anything. Logs are kept 14 days, and a test checks that no password, recipe, shopping or typed-link text reaches them.
- **A hardened data folder (D2).** Files in the data folder are 0600 and folders 0700, set at start-up and fixed for installs from before; if a path can't be restricted the start-up warning names the first one and points to `docs/hardening.md`. The compose example now has no-new-privileges, all capabilities dropped, a read-only root with a tmpfs, an init process, a memory limit and a commented `user:` line. The image carries OCI labels, and the release build's SBOM and provenance are written up.
- **Update check and About (X1).** About shows the version, its release day, and how old this version is from 3 months. A **Check now** button for admins always works: one request to the public release list through the outbound gate, whatever the daily switch says (cabledrawer 12 Nov). The Privacy switch **Check for updates daily** (off at first) only controls the automatic check. A newer version shows "Update available" in Settings and "New version ready" asks you to close every tab and open Mealwright again. **Until 1.0 the release list's address is a placeholder, so no check connects and Check now says it couldn't check.**
- **Report a problem (X2).** About › Report a problem builds a report on the server with names, recipes, pantry contents, server addresses, e-mail addresses and secrets removed. You see every line, change or remove any (with Undo), add what you were doing, then Copy, Download or Open on GitHub yourself: Mealwright never sends it. A person's, household's, recipe's, ingredient's, shop's, place's, list's or tag's old name is removed too after a rename or delete, kept a day longer than the logs (15 days) in a new table (`former_name`); only an admin's report has errors from the server's log (up to 20 from the last 24 hours, only since the last Delete everything).
- **Install guide and proxy examples (M1).** `docs/install.md` says why HTTPS is needed, to give Mealwright its own host name, and what `MEALWRIGHT_TRUSTED_PROXIES` does. `docs/proxies/` has an example each for Caddy, Traefik, nginx and Nginx Proxy Manager. `scripts/test-proxies.sh` (not part of `./check`) tries their headers in throwaway containers; Nginx Proxy Manager itself isn't started.
- **Settings in the spec's order, from one list (U1).** Appearance, Amounts, Household, Meal slots, Shops & places, Privacy, Sign-in, Your data, About (with Your kitchen and Recent changes among the kitchen sections), the same on the computer's list and the phone's groups; the phone also has a Mealwright group with About and Report a problem. About gets "Licences and credits": the licence, a plain link to the source (no request is made until you click), the USDA FoodData Central credit and the fonts' licences. A test fails if some part of the code uses an outside connection that Privacy has no switch for.
- **Onboarding and Amounts (U2).** After the admin account is made, onboarding shows once for the household: six steps on a phone, one page of cards on a computer: how amounts are shown, who eats here (names only), shops and a starter pack, each optional. On a phone Skip passes over just that step (the last Skip, Finish setup or Go to Today finishes it and never shows it again); a computer's page has Finish setup only. Households from before this version count as done. Settings › Amounts: **As the recipe says** or **Metric: grams and ml** (admins; in Recent changes with Undo). The choice is kept; grams and millilitres on screen come in a later version, and cups after 1.0.
- **Single sign-on (O1).** An admin sets it up on a computer in Settings › Sign-in › Single sign-on (a phone says "Set up on a computer"; proposed, for cabledrawer): the sign-in server's issuer address, client ID and secret, the callback address to give it (this browser's own, saved and checked on every sign-in), which groups become Admin or Member, and what "Anyone else" gets (Not let in by default; proposed, for cabledrawer). Sign in then shows "Sign in with …". Sign-ins use PKCE (S256), a one-time state and nonce kept only in a sealed, HttpOnly cookie in the browser that started, and an ID token checked for issuer, audience, nonce, expiry and a public-key signature. A sign-in server that didn't answer isn't asked again for a minute. Logins are linked only by the sign-in server's issuer and subject; a new person gets an account on first sign-in (proposed, for cabledrawer), and a user name already taken is refused with a clear message.
- **Single sign-on: password sign-in can be turned off** (Sign in then shows only the button), but only while an admin has signed in by single sign-on, or has linked themselves after the setup's test (proposed, for cabledrawer). The test links nobody: it starts with a button on the setup screen, asks the sign-in server who you are, and, only when it makes that person an Admin, asks "Link tess to …?" with their name and email address; nothing is linked until the admin presses Link (proposed, for cabledrawer). Passwords count as off only while single sign-on can really start: with the Single sign-on switch off, or when the saved secret can't be read (the key file is lost), or when the sign-in server isn't on Your own network any more, passwords work again, so nobody is locked out (proposed, for cabledrawer). While password sign-in is off, saving a change to who gets in turns it back on and says so, and it can't be turned off in the same save as such a change.
- **Single sign-on: Privacy, secrets and refresh.** A new Privacy switch, Single sign-on, off until an admin turns it on: every request to the sign-in server goes through the outbound gate under it. A sign-in server on your own network needs listing in Privacy › Your own network. The client secret is encrypted (JWE, dir with A256GCM) with a key file the server makes in the data folder (`secret.key`, readable only by Mealwright, written whole and then put in place); it is never sent back, shown or logged. Refresh tokens are encrypted the same way; once an hour the server asks the sign-in server whether each sign-in is still good and signs out someone whose account was removed or disabled there (signing out at the sign-in server alone doesn't end a Mealwright sign-in; a sign-in from another issuer is not asked about, and a changed issuer or client ID drops the refresh tokens). `offline_access` is asked for when the server lists it; if a sign-in is refused for that, Mealwright tries once more without it and keeps no refresh token (proposed, for cabledrawer). **Back up the key file with the database**: without it the secret must be typed in again.
- **API tokens (O2; proposed, for cabledrawer).** Settings › Sign-in › API tokens (admins only): make a token for another app on your own network, like Home Assistant, that can read, or read and change, the household's data, and that never expires or ends after 30 days, 1 year or on a date you pick (at most 5 years ahead). It is shown once, with Copy; only its SHA-256 is kept. Delete asks first, and the apps using it stop at once. At most 50 per household. **Using one:** send `Authorization: Bearer mw_…` to `/api/v1`. A read-only token gets 403 on anything that changes data. A token that doesn't work (unknown, deleted, ended, or its admin removed or made a member) always gets the same 401. A token never makes, lists or deletes tokens, never changes passwords or where you're signed in, never answers "Who's this?", never changes people, roles, the Privacy switches or your own network, and never touches Your data (the export, the backups' settings, Back up now, Delete everything): all 403. A request that sends both a token and a sign-in cookie is refused (400). Live updates (`/events`) still need a sign-in. Logs say "API token made by tess" and "API token deleted by tess"; the token itself is never logged and using one writes nothing.
- **A token acts as the admin who made it,** and only while they're an admin: made a member or removed, every token they made is deleted at once, and Undo doesn't bring them back. They also stop when single sign-on's groups make that admin a Member, when the sign-in server ends their sign-in, when "Sign out my other devices", "Sign out everywhere else" or the reset-admin command sign that login out (the screens say so), and when single sign-on refuses a known admin (removed or not let in) (all proposed, for cabledrawer).
- **Single sign-on's last-admin rule (proposed, for cabledrawer).** When the groups would make an admin a Member, they stay an admin if no other admin could get in again without the sign-in server's say (a working password, or a sign-in that hasn't run out and could be started again, linked to the saved sign-in server; being linked alone isn't enough). When single sign-on refuses a login that has an account, its sign-ins and tokens end; but the household's last admin who no other admin can stand in for keeps their sign-ins when refused, and their tokens stop (they keep tokens too only while password sign-in really works for them). With password sign-in off, the hourly check also keeps the only admin who can get in signed in when the sign-in server stops accepting them, stops their tokens, asks again every 10 minutes, and shows admins in Settings › Sign-in › Single sign-on: "The sign-in server no longer accepts <name>. Mealwright kept them signed in because they're the only admin who can get in. Fix it at the sign-in server, or turn password sign-in back on." (cabledrawer 12 Nov). With password sign-in on, the only admin who has no password is kept the same way (the warning ends "…Fix it at the sign-in server."; proposed, for cabledrawer). **A refused login that is kept is marked in the database** until they sign in again and the sign-in server's groups make them an Admin, or another admin makes them a Member or removes them (a sign-in that is merely renewed doesn't end it, and the warning stays while the mark does; proposed, for cabledrawer): while marked, they can't make API tokens ("The sign-in server no longer accepts you, so you can't make API tokens."; proposed, for cabledrawer), and a token made after the refusal never works, even after they sign out or the server restarts (database change `e5b3c9a1d742`; going back drops the mark; cabledrawer 12 Nov). **A kept admin is still a full admin** (cabledrawer 12 Nov): the mark stops the direct route, not an admin using admin powers. To remove someone, first make sure another admin can get in, then remove them in Settings → Household; disabling them only at the sign-in server isn't enough while they're the only admin.
- **Finish setup (cabledrawer 12 Nov).** An admin who hasn't finished onboarding isn't sent back to it; Settings shows a **Finish setup** row ("A few quick things: amounts, household, shops.") on the phone's list and the computer's until it's done. Members never see it. Its tick icon is proposed, for cabledrawer.
- **Licence notices in the image (cabledrawer 12 Nov).** `/third-party-licences.txt` lists every library and font the web app carries, with their licence texts, taken from what the build actually bundles (a test fails if one is missing). The Python libraries keep theirs in the image. "Other open-source parts" stays out of About for 0.9.0.
- **Export and restore.** The export leaves out API tokens, the single sign-on client secret, the refused-login mark and the old names kept for Report a problem (the rest of the setup is exported; the secret is typed again if an export is ever put back) (proposed, for cabledrawer).
- New library: Authlib 1.6.12 (BSD-3-Clause), which brings cryptography (Apache-2.0 or BSD-3-Clause). Its HTTP clients are not used.

### Changed

- **Leaving a page (T1).** A request cut off because you left the page is neither shown nor logged as a failure; a page that shows again, or no `pagehide` within 3 seconds, ends the leave; sign-out retry and cut-off imports respect a leave.
- **All recipes** is one list for both layouts, so crossing the panes' width keeps its rows, search and tag.
- **Outbound gate:** a request has a time limit on the whole request (30 seconds, or the caller's, cut to 120 seconds), the slow body included; it can now POST.
- **Your data's password check** counts wrong tries like sign-in does.

### Fixed

- **Many requests at once no longer fail or stall.** About 60 signed-in requests in the same moment used to leave most of them with an error and everyone waiting 30 seconds (the database connections ran out; older than 0.9, found by a security review). Now at most 40 requests use the database at a time and the rest wait their turn, a request gives its connection back before its answer is sent, and a photo upload holds nothing while the photo arrives (its sign-in is checked before the photo is read, and again once it's in). Nothing on screen changes.

### Security (0.9 A2, sign-in hardening)

- **Known devices.** A device that has signed in as someone gets a "known device" cookie for a year, and isn't held up when someone else's wrong guesses pause that username (its own wrong passwords give it the same pause). Changing the password forgets every known device except the one that changed it; Sign out everywhere else doesn't forget them. A planted device cookie with odd entries is read strictly: the odd entries are dropped.
- **Just after a new password.** For ten minutes after a password is changed (Settings, or reset-admin), the username's pause doesn't stop its owner's right password; wrong ones still count, still meet the address limit and get the same words.
- **Setting up a fresh install needs a setup code.** Before anyone has an account, Mealwright prints a setup code in its log each time it starts, and the first-run page asks for it, so only someone who can read the server's log (`docker logs mealwright`) can create the admin account. An install that already has an account doesn't see it.
- **A way back in for the only admin:** `docker exec -it mealwright python -m mealwright reset-admin <username>` sets a new random password for that admin, prints it once and signs them out on every device. It works only for an admin who hasn't been removed.
- **Settings → Sign-in:** change your password (it signs your other devices out unless you switch off "Sign out my other devices"), see where you're signed in, sign out one device, or Sign out everywhere else.
- **Behind a reverse proxy:** if requests come through a proxy that isn't trusted, Mealwright logs a warning once after it starts ("A request came through a reverse proxy…"), because then every visitor looks like the proxy and one person's wrong passwords slow down everyone. Set `MEALWRIGHT_TRUSTED_PROXIES` to the proxy's address or network and restart.
- **A removed person keeps no sign-in.** A device signed in as someone stops working the moment they're removed, even one that signed in at the same moment as the removal (release security pass).

- **A flaky test now fails the check twice in a row (T2a).** A browser test that fails and passes on its retry in two completed full runs in a row, or even once in a spec file that is new on the branch, fails the check ("browser: flaky twice", "browser: flaky (new tests)"). The history, keyed by "[project] file › title", is kept in `.check-history/` in the main checkout (not in the repo) and only a completed full run writes it. An error from `e2e/scripts/flaky.mjs` is a failure, never "no flaky tests". The rule has script tests with made-up reports (`e2e/scripts/flaky.test.mjs`, run by `./check`).
- **`./check --rerun-failed` (T2a).** Runs again only the browser tests that failed in the last full run of the same folder, even one stopped early (its reports are kept in `.check-history/last-run/`; the summary says "that run was stopped early (<reason>)" when it was), each stream with its own servers, on the current commit; the summary says "DIAGNOSIS RUN, NOT valid for a pull request" and names both commits.
- **`./check --browser-files <spec file>...` (T2a).** The early run for a pull request: only those spec files, on desktop, phone and WebKit side by side, with one test server per stream (the first-run and strict servers only when `sign-in.spec.ts` is listed, the screenshots server only for `screens.spec.ts`, set by the new `E2E_SERVERS`), `screens.spec.ts` added when the branch changes `frontend/src`; `--update-snapshots` works only in this mode, for the two screens projects only. Not valid for a pull request.
- **`./check --scan-only` (T2a).** pip-audit, Bandit, osv-scanner, then a fresh image of the current commit (its own tag) and Trivy, with no tests. Every `./check` mode takes the same machine-wide lock.
- **The fast check installs when a library changed (T2a).** `./check --fast` uses the full check's install fingerprint (now with `.npmrc` in it) instead of re-using any `node_modules`.
- **Smaller `./check` fixes (T2a).** It stops cleanly on a closed terminal (HUP) and stops every background job on exit, which closes the gap between starting a step and noting its process number; the scanners also run when `.dockerignore`, an `.npmrc` or any `osv-scanner.toml` changes, and the Scanners line says when origin/main was last fetched more than 24 hours ago; a failed browser install keeps its failure note; the frontend unit tests use the run's temp folder.
- **One test server per worker (T2b item 1, cabledrawer 8 Nov).** Every Playwright worker starts its own Mealwright server (the same test launcher and clock shift as before) on its own port and data folder, creates the admin, saves its own sign-in, and removes the folder when it ends (`e2e/tests/clock.ts`); nothing in Mealwright itself changes. Specs that named the main server now use the worker's (`app`, `baseURL`, `storageState`). The first-run, strict and screenshots servers stay shared. `E2E_WORKERS` sets the workers per stream (up to 6); `./check` runs desktop 3, phone 2 and WebKit 2 (cabledrawer 8 Nov, T2c: 4, 3 and 2 took the load to 35 on 12 cores; `CHECK_WORKERS_DESKTOP`, `CHECK_WORKERS_PHONE`, `CHECK_WORKERS_WEBKIT`) and says so in each browser step's note. A restarted worker waits for its port to be free, so it never uses its predecessor's server, and a worker's server stops within a second even when the worker is killed. The summary also has a "Settings:" line, and a full run with `CHECK_STOP_EARLY=0` or its own `CHECK_HISTORY_DIR` says it is not valid for a pull request.
- **`./check --fast` runs the backend tests a change touches (T2b item 2).** `e2e/test-map.json` maps code areas to backend test files and browser spec files (and the words in `docs/dev/words.md` or the web app to the specs that look for them); `--fast` runs the mapped backend tests for the branch's changes, says which and why, and prints the `./check --browser-files ...` command for the browser files; `--fast --all` runs all. Every `./check` fails when a backend test file or a spec file is not in the map. The full check still runs everything.
- **`pantry-list.spec.ts` runs on desktop only (T2b item 3, cabledrawer 8 Nov, option A).**
- **A failed full check lists what to put in the fixes PR (T2b item 4).** `e2e/scripts/fixes-list.mjs` names each failed browser test by the PR that last changed its spec file on the line (from the commit subject), printed at the end of the run and kept in `.check/fixes-list.txt`.

**Before you install it: back up your data.** This version changes the database (new tables and columns for cooked records, ingredient links on method steps, who eats each meal, notes on the plan, cooking per step, and a staple's restock date and when it was typed; nothing existing is rewritten), and the old version can't read a database the new one has changed. The steps are the same as before (`docs/dev/test-on-homelab.md` section 4.1: stop Mealwright, then back up the data folder). From this version Mealwright also makes its own safety copy of the database before every upgrade (see Added, K1), but that copy holds only the database, not the photos, so keep making the backup.

### Security

The security passes on each 0.7 pull request and on the fixes before the first test build found these before release; cabledrawer's own household is the only one each could reach.
- **Sync:** an Undo sent with an impossible phone clock (year 1 against year 9999) gave a server error and stopped that phone's queue; an impossible clock is now ignored. A "put away" with a use-by date did the same and now sets the date. Every date and time a phone sends was tried at the extremes and in odd forms (1,089 batches): no server error, and the next change in the queue always goes through.
- **Extreme dates:** a staple's restock date in year 1 or 9999 could break the Pantry and Ingredients pages for the whole household; dates before 2000 and in the future are now refused, and a bad stored date breaks no page. - **Cooking:** a note like "99999999999999999999999999999 cloves" (or in other kinds of digits) gave a server error on "Cooked it" for that recipe; a count is now one to four plain digits. A choice sent with a made-up ingredient key ("food:²", or a 30-digit number) gave a server error and is now refused cleanly. Every link, and every place it sends you on to (at most 5), is checked before anything is sent: web links only, ports 80 and 443 only, and public addresses only. The request goes to exactly the address that was checked, so a site can't pass the check and then point somewhere private. A slow site is cut off after 15 seconds, and a whole fetch, redirects included, after 30. Pages up to 5 MB, web pages only; photos up to 15 MB and 50 megapixels, then shrunk and cleaned like an uploaded photo (hidden details such as the place it was taken are removed). Log lines never say which site was visited. How it works: `docs/dev/recipe-import.md`.
- **This server itself, link-local and cloud "metadata" addresses are never visited**, whatever the settings.
- **The "Your own network" list, on the server** (the screen comes later in 0.5): addresses on your home network (your router, a home wiki) are refused unless an admin puts their name, address or range on this list, which also opens other ports for them. It starts empty, belongs to the household like the Privacy switches, and refuses anything always blocked, ranges that are too wide, and more than 100 entries. This adds one database table; nothing existing is rewritten.
- **The page reader** reads the recipe data most recipe sites include for search engines (schema.org JSON-LD, and microdata on older pages), with Python's own tools and no new libraries: the name, a short description (cut at 200 characters), total time, Serves or Makes, nutrition per serving, the ingredients and method with their section names as headings, the category and cuisine as tags (never the page's keywords), the main photo and the author. Up to 200 ingredient lines and 100 steps are kept, and the import knows when a page had more. Hidden characters are taken out of the page's text; Tamil and Hindi names keep the joiners they need. Tested on made-up pages shaped like eight kinds of recipe site; no real page is stored in the repo. A page that tries to make the reader slow or greedy (very long numbers, thousands of tiny JSON objects, and the like) is cut short, and as a safety net for anything not yet thought of, each page is read in a separate short-lived process with a time limit and a memory limit (384 MB): past either, the import says "Couldn’t read that page. Paste the recipe’s text instead." (The time limit is now counted in the child's own processor time, 12 seconds, with a 15-second clock backstop; see the 0.5 PR 3 entry.)

### Changed

- **The time limit for reading a page** counts the reading process's own processor time (12 seconds) with a 15-second clock backstop, instead of 5 seconds of clock: the realistic big test page needs about 1.2 seconds of processor time on a fast PC, perhaps 5 to 6 seconds on a Raspberry Pi 4 class board (an estimate), which the old limit could have refused. The reading process also can't write a core file, and it switches on the network guard itself (it starts fresh, so it doesn't have the server's). The guard now lives in its own small module (`network_guard.py`), so the reading process starts in 0.1 second instead of 0.9. A result that can't be sent back, or a reading process that dies, is "crash" in the log, not "memory", and a process that answered but doesn't end is killed after 2 seconds.

### Fixed

- **The name look-up now counts towards the import's 30 seconds (spec section 6, question 40).** Finding a site's address from its name could run past the 30 seconds if the computer's name service was slow; it now waits at most the time the import has left, and then says "That site took too long to answer. Try again later." This covers the link, each place it sends you on to, and the photo. Anything else that looks up a name through the outbound gate waits at most 15 seconds. No new connection is made and the database is unchanged.
- A page whose total time was a superscript or circled digit ("²", "①") raised an error instead of being read as no time.
- A control character between words (U+001C to U+001F) joined them, and private-use or unassigned characters stayed in an ingredient line; a cut no longer splits a country flag or a skin tone, and a text of only combining marks is cut at the limit, not to nothing. An amount that converts to more than 1,000,000 g or ml no longer counts.
- The real-recipe check script stopped before reading any page when run on its own: an import loop that the tests hid, because they load the app first. Its first real run (24 Oct) fetched every page but read none. A test now starts the script in a fresh Python, both as a person runs it and as the page reader's own process loads it.
- **Shopping, "Different pack?" → Other…** no longer sends 1004.9999999999999 for 1.005 kg, which the server refused; it sends 1005.
- **Security (0.5 PR 7):** a photo file that can't be deleted (the hourly sweep, an upload's clean-up, or the clean-up inside writing the files) logs only the kind of error, never the file's path; Undo's remaining restore steps (`_restore_field`, `_name`, `_size`, `_stand_in`, `_conversion`, `_lot`) check the household themselves, with a two-household test for each; "Your own network" refuses `localhost.localdomain`, `ip6-localhost`, `ip6-loopback`, `localhost6`, `metadata.google.internal` and an old-style address that means this server or a metadata address (`0x7f000001`, `0177.0.0.1`, `0x7f.1`, `0xa9fea9fe`, `0x`) with the "always blocked" sentence (any other old-style address, such as `0xc0a80001`, or one with a digit that isn't octal, such as `09.1.1.1`, gets the bad-entry sentence, so write it as `192.168.0.1`), and a fetch refuses those names too.
- **Shopping, Undo of an add that joined a line (0.5 PR 8).** If you add 2 L of milk and it joins the 1 L already on the list, and that line is ticked afterwards (bought, 3 L), Undo of the add now leaves the line alone and says "Nothing to put back: it has all changed again since." It used to lower the amount of a line that was already bought. The same rule already held for Move.
- **Import (0.5 PR 8):** if saving a downloaded photo fails and the clean-up of its files fails too, the request now shows the first error (not the clean-up's), and the log says only the kind of error, never a file's path.
- **A request with half a character in it (0.5 PR 8).** A JSON request containing a lone surrogate (such as `"\ud800"`, half an emoji) now gets a 422 "unprocessable" answer like any other mistake; inside a queued offline change, the change gets a plain refusal instead. Neither is a server error (500) any more. The error answers no longer repeat the text that was sent.
- **The real-recipe check script (0.5 PR 8):** `www.example.com` and `example.com` count as one site, so they share the 5-second gap.

On the phone a toast says where it went, with **Change** (another place) and Undo; on desktop a **Put away** panel beside the list does the same. Unticking, or Undo, takes it back out and never takes the pantry below zero. **Different pack?** changes what the pantry got ("What did you buy?"), and an item with no amount offers **How much?** instead. Staples and items with no amount put nothing in the pantry. Every tick shows in Pantry's Recent changes ("Bought 2 packets Toor dal → Cupboard") with Undo.
- **Two phones, one list.** Nothing is ever refused with a pop-up because someone else changed the list: the server applies changes in the order it receives them, and where it matters it leaves a **quiet note** under the item, with Undo and a dismiss button, such as "Wren had removed this. Your tick still went into the pantry.", "Wren added milk too" or "Wren changed Milk to 2 L" ("Your other phone" when it was you). Nine kinds of clash have a note (N1 to N9 in `docs/dev/sync-protocol.md`).
- **"Did you buy 2?"** When two phones tick the same item while offline, a card asks, with **Yes, 2** and **Just 1**; the first answer settles it for everyone, and Undo brings the card back. Just 1 takes the extra packet back out of the pantry.
- **Sync for phones** (`POST /api/v1/shopping/actions` and `GET /api/v1/shopping/changes?since=N`): a phone sends a batch of its changes, each with its own ID so that sending one twice does nothing the second time, and gets back an answer for each and everything that changed since it last looked. The batch is described in `docs/dev/sync-protocol.md`, and both are in the OpenAPI document.

**Offline**

- **It works without a connection.** Ticks, adds and every other change to a list are kept on the phone, shown at once, and sent when the connection is back: one batch at a time, in order, tried again after a pause if the server can't be reached. Closing the app doesn't lose them. (iPhone Safari can clear a web app's saved data after about 7 days without use; adding Mealwright to the Home Screen helps.) While offline the bar says "Offline — 3 changes waiting" (on desktop "3 changes waiting. They'll save when you're back."), Shopping's subtitle says "12 to buy · offline, saving on this phone", and when everything is sent a toast says "Back online — all saved".
- **Opening the app offline.** The app opens as the person last signed in on that phone, and Shopping works from the phone's copy, including finding ingredients in the add box. Pantry, Ingredients and Settings need your server: offline they say "You're offline. Pantry needs your Mealwright server — your shopping list works offline." with a Shopping button. Settings still has Sign out and the theme switch, and "+ Add to pantry" says it needs the server. A phone that has never loaded the list says "Your shopping list isn't on this phone yet. It'll be here after you've opened it once while connected."
- **Signing in running out doesn't lose changes.** If your sign-in runs out while offline, the changes stay on the phone: "Please sign in again. Your 3 changes are kept on this phone." Signing back in as the same person sends them at once. A different person is warned first ("Wren's 3 changes haven't been sent yet. If you carry on, they're lost.", with "Sign in as Wren instead" and "Carry on and lose them") and nothing is ever sent under their login.
- **A different login always starts clean.** When someone else signs in on a phone, its offline copy is wiped, as at signing out, and the next start makes a new device ID. A wrong password wipes nothing.
- **Signing out sends first.** Sign out tries to send what is waiting. If something is still unsent: "3 changes haven't been sent yet. If you sign out now, they're lost." with Try sending now, Stay signed in and Sign out and lose them. Signing out wipes the phone's offline copy (the offline database, saved lists and ingredient names, and everything the app kept for the household in the browser), and other tabs of the app clear themselves and go to the sign-in page.
- **A storage error is never "nothing waiting".** If the browser can't read the app's offline store, nothing is deleted or written on that result. The same login carries on (cabledrawer 18 Oct): it never wipes anything. Anyone else pressing Sign in is told "This phone couldn't check for changes waiting to be sent. Nothing has been deleted.", with Try again and "Carry on anyway — anything waiting on this phone may be lost". Settings says the same instead of signing out, with Try again, Stay signed in and "Sign out anyway — anything waiting on this phone may be lost" (cabledrawer 18 Oct). Both "anyway" choices wipe as usual.
- **Signing out loses only the changes the warning showed.** If another tab queues more after "3 changes haven't been sent yet" appears, "Sign out and lose them" warns again with the new count instead of losing them. Adding a change and wiping take turns across tabs (the browser's Web Locks), so a change added at that moment is never lost unseen.
- **A phone that can't delete its offline copy lets nobody in.** If a wipe can't delete the offline store, it is never opened or used again, the session is still ended, and the sign-in page says "This phone couldn't delete its offline copy of the household. Nobody can sign in on it until that's done. Close other Mealwright tabs or restart the browser, then Try again." with a Try again button (cabledrawer 18 Oct). Until Try again has deleted it, the whole sign-in form is disabled (cabledrawer 18 Oct).
- **Carrying on loses only the changes the warning showed.** The sign-in warning remembers which of Wren's changes it showed. If another tab has queued a different one since, it warns again with the new count instead of losing it.
- **No bouncing when the server won't sign out.** If the server answers the sign-out with an error, the sign-in page stays and says "Couldn't finish signing out on this phone." with Try again, instead of going back and forth between the app and the sign-in page. Nothing is deleted. A Try again the server refuses says it again, read out.
- **The sign-in page says why you were signed out** (cabledrawer 18 Oct): "You were signed out because Wren's 3 changes are waiting on this phone. Sign in as Wren to send them." ("Wren's change … to send it" for one; "this computer" on a computer.)
- **Sign in is busy from the first press.** Sign in shows "Signing in…" and ignores a second press (or Enter) straight away, so a quick second press can't start a second sign-in while the phone is still being checked.
- **"Couldn't finish signing out" has a grey Try again**, the quiet look, on that screen only; every other Try again is the main button.
- **"Still stuck?" under the offline copy message.** Under "This phone couldn't delete its offline copy of the household…" one small line says: "Still stuck? Clear this site's data in your browser's settings." The README has a matching Troubleshooting entry.

**Live updates, installing and connection**

- **Live updates.** A second phone or window sees a tick, an added item or a pantry change within a moment, without reloading. They come from your own Mealwright server only (`GET /api/v1/events`, Server-Sent Events); the stream carries numbers, never names. An open screen doesn't count as activity, so the 12-hour sign-out still happens; a kitchen tablet should use "Remember this phone".
- **Installable app.** A manifest, icons made from the brand icon, and a service worker that keeps only the app's own files, so the app's own files (its code, fonts and icons) load without a connection. The screens still need your server; Shopping works offline from the phone's copy (see Offline above). It never keeps anything from the server (`/api`) and never updates itself mid-use: a new version starts the next time every window has been closed. No Install button yet.
- **Connection bar.** "Offline" with Try now on every page (above the tabs on a phone, at the foot of the sidebar on desktop), a short "Back online" toast, and "12 to buy · offline" on Shopping. A blip under 3 seconds shows nothing. With changes waiting it says "Offline — 3 changes waiting" (see Offline above).

**Pantry and Ingredients**

- **Tap a staple to add it to the shopping list.** On Pantry, a staple chip adds that ingredient to the main shopping list with the toast "Oil added to the shopping list · Undo". A small tick shows on the chip while it is on the list; tapping a ticked chip adds nothing more and says "Oil is already on the shopping list." The tap goes through the same add action and waiting list as Shopping, so a tap made while the connection is failing is kept on the phone and sent once, when the server is back. Screen readers hear "Add Oil to the shopping list" or "Oil, on the shopping list". An "Edit staples" link under the chips opens Ingredients with the Staples filter.
- **"+ List" on running-low rows** (hidden in 0.2 until the shopping list worked) does the same for that ingredient (toast with Undo, tick, "already on the shopping list", works through the waiting list).
- **Recent changes on Ingredients.** New ingredients, Staple on or off, removals, merges and edits, each with Undo for 7 days: on desktop a one-line "Recent changes · 9" bar above the editor ("· 10+" past ten) opens the list in the side column; on the phone a "Recent changes" button opens a sheet. It updates after changes you make here, when stock changes anywhere, and when you come back to the page; an ingredient edited on another phone doesn't appear live yet. Pantry's Recent changes still lists stock changes only.
- **Server:** `GET /api/v1/changes?area=ingredients` lists ingredient changes (and their Undos) only, for your household only. No database change for this.
- **Marks in an opened Pantry row.** An opened row with a single packet shows the ¼ · ½ · ¾ · Full marks, with "About 250 g left · type it instead" under them (the link opens the packet menu at "What's left", with the box ready). In a narrow desktop column the marks go two by two, each at least 44 px wide. If saving a mark fails, its tick goes back. The arrow keys move between the marks.

### Changed

- **Collapsed sidebar:** the Recipes icon opens a small pop-out with All recipes, Drafts and Ingredients, the current page marked. It works with the keyboard and screen readers (a menu).
- **Add to pantry:** "Pick a date" opens the phone's date picker straight away and then shows the date it chose ("Sat 24 Oct") on the chip. The separate Date field is gone, and cancelling the picker changes nothing. The Use-by chips now choose as the arrow keys move, like the app's other chip groups; "Pick a date" opens its picker only on Space, Enter or a tap, never just because focus arrived on it. Screen readers announce the chip once, not also the hidden date field behind it.
- **Pantry search** shows one list of results, each with its place ("Toor dal · Cupboard") and "also called thuvaram paruppu" when another name matched. On the phone there is a "Search pantry" field above the tabs, with the same one-list results.
- **Undo says what it undid:** "Undone: Removed Oil from Ingredients", for Ctrl+Z and the toast's Undo.
- **Use soon card:** "Lemon · Today" and "Tomorrow" start with a capital, like the Today chip.
- **Recent changes shows its verb in bold** on every change worded verb first: Added, Removed, Renamed, Merged, Undid, "Added other name …", "Removed other name …" and "Forgot your weight of …". An ingredient that happens to be called "Added sugar" is not bolded by mistake.

### Database

- **One migration** (`f509d7a1c609`): six new tables for the shopping lists (`shopping_list`, `list_item`, `list_tick`, `sync_action`, `list_note` and `double_tick`), `aisle` and `version` on ingredients, `tick_id` on changes, and `list_seq` and `list_purged_seq` on the household. It makes each household's main list "This week" and gives existing ingredients a starting aisle from the bundled table. Nothing existing is rewritten. Checked by tests that build a 0.2.1 database with real-looking data, upgrade it, and also go back down and up again.
- Old shopping-list notes and answered questions are tidied away after 7 days, and removed lists and lines after 12 months, by the same hourly background job that summarises old pantry history. A phone that was behind a tidy-up gets a fresh copy of the lists; changes still waiting on it are kept and sent after.

### Privacy and security

- **Nothing new leaves your server.** Live updates, the sync endpoints and the app's service worker talk only to your own Mealwright server, and the conversions table and the "How do you count it?" guess stay on it too.
- **The live stream carries numbers, never names.**
- **Every `/api` answer is sent with `Cache-Control: no-store`, and the service worker never keeps anything from `/api`.**
- **What the phone keeps, and when it goes.** The offline copy of the lists lives in the browser's own database (IndexedDB). Signing out, or a different person signing in, wipes it, along with the app's other saved data about the household. A sign-in that merely runs out keeps it on purpose, so the changes waiting aren't lost. Besides the theme and sidebar choices and two flags for an unfinished sign-out or wipe, the only thing put in `localStorage` is the last login's number and username (no password or session), so the app knows whose phone it is when the offline copy can't be read; the wipe removes it too.
- One household can never see or change another's lists, notes, questions or changes (tested on every endpoint). An ID from another household is answered exactly like one that doesn't exist.

### For developers

- New dependency: **idb 8.0.3** (ISC; approved by cabledrawer 17 Oct), a small helper for the browser's IndexedDB. No other new dependency.
- The sync protocol is written up in `docs/dev/sync-protocol.md` and tested with two- and three-phone tests (random queues from several phones keep the pantry and the list honest); the Shopping screen writes only through one function, `sendAction`, that puts a change on the phone's queue first.
- `GET /api/v1/changes?area=ingredients` lists ingredient changes only, for your household only.
- `docs/dev/test-on-homelab.md` explains how to build the image, copy it to the server and go back; no registry is used in 0.x.

cd ~/mealwright

- **A blocked outside connection is logged in plain words and names only the switch** ("recipe import is switched off"), never the site or address, which could show what someone was cooking. A test checks it. (Asked by cabledrawer.)

## [0.1.0] - 2026-10-17

Milestone 0.1, Foundation: an empty but real Mealwright you can install, sign in to and click around, with the safety rails built in. Not published; for testing on cabledrawer's homelab.

### Added

- **One Docker image** with the web app and its API. It runs as an unprivileged user (UID 10001), keeps everything in `/data`, has a health check, and contains no `pip`. `compose.example.yaml` shows how to run it behind a reverse proxy.
- **First run:** the first visitor creates the admin account (there's no default admin), then the app opens.
- **Sign in and out**, with "Remember this device" for 30 days. Passwords need at least 10 characters and are stored scrambled (Argon2). After 5 wrong guesses, sign-in slows down, per account and per real address, so one person's guesses don't slow down anyone else.
- **The app shell:** bottom tabs on phone and a collapsible sidebar on desktop, with empty Today, Plan, Shopping, Pantry and Recipes pages and a Settings page with Sign out.
- **Auto · Light · Dark** in plain sight, saved to your account. A designed dark theme, with fonts bundled.
- **One switch component** for every on/off.
- **API** under `/api/v1`, described at `/api/v1/openapi.json`. `GET /api/v1/version` reports the version for update tools such as Diun.
- **Database changes are applied on start-up** (migrations: household, Privacy switches, logins and sessions).
- **`./check`** runs every check before each pull request: lint, types, tests, browser tests, licence allow list, pip-audit, osv-scanner, Bandit, and Trivy plus a no-telemetry check on the image.
- Licence (AGPL-3.0), README, contributing guide, security policy, this changelog, and the homelab testing guide (`docs/dev/test-on-homelab.md`).

### Privacy and security

- **The outbound gate:** the only way Mealwright connects to anything outside your server. Each kind of connection has its own Privacy switch, and **all of them are off**. While the app runs, any other connection or address lookup is refused, whether it comes from our code or a library.
- **No telemetry:** FastAPI's built-in telemetry is switched off, and no telemetry package is installed (checked in the code and in the image).
- **Strict browser rules (Content Security Policy):** pages load files only from your own server. A real-browser test proves an outside script is blocked. Location, camera and microphone are off; referrers aren't sent.
- **Logs** hold only sign-ins and errors, never what people view or search for (the web server's request log is off).
- **HTTPS is required for sign-in.** On a plain `http://` address, Mealwright says so instead of failing silently; `MEALWRIGHT_ALLOW_PLAIN_HTTP` allows it for testing, with a warning.
- **Works behind any reverse proxy.** Its forwarded headers are believed only from `MEALWRIGHT_TRUSTED_PROXIES` (off by default).
- Requests from other sites are refused, and the session cookie can't be read by scripts and is stored only as a fingerprint.
